# Solo-Lab 的飞书项目模板

Solo-Lab 插件把飞书项目空间当任务台账用。空间里有哪些工作项类型、每类怎么走、每一步必填什么，由这个模板决定；插件不内置这些结构，运行时读空间。模板的版本号从 1.1.0 起和插件对齐，见“版本规则”。

## 模板里有什么

五类工作项，都用节点流程，每个流程以书记员确认的“归档”节点收尾。

| 类型 | 用途 | 流程 |
| --- | --- | --- |
| 研究任务 | 主线。一个空间可以有多条 | 正式实验：九步加归档；探索：定方向、探索、提出假设、归档 |
| 同序列需求 | 序列内委托和交付 | 定方案、执行、验收、归档。承接的 +0 先交方案，发出方确认了才执行 |
| 跨序列需求 | 序列之间 +1 对 +1 的请求 | 提出、接单、执行、验收、归档 |
| 决策 | 研究员拍板和签字 | 决定、归档；状态依次是待决定、待执行、归档 |
| 反馈 | 导师和研究员的反馈 | 解析、归档 |

每个节点联动一个角色，关卡只有一种：节点完成表单里的必填字段。节点不设“负责人必填”、排期、估分、节点任务和显示条件。模板配工作项类型、字段、节点流程（含角色和状态）和新建页；决策另配详情页上的两个字段、默认表格列和“待定决策”视图。其余视图、详情页布局、权限和自动化用飞书的默认值。

## 待定决策视图

研究员要处理的决策都在空间置顶的“待定决策”视图里：状态是待决定的决策，加上状态是待执行、执行方是研究员的决策；先按紧急程度、再按创建时间排。每行带执行方和研究员要做的事。

决策登记时，插件把决策包包头的“执行方”和“研究员要做的事”写进同名字段。确认“决定”以后决策进入待执行：执行方是会话的，这一条离开视图，会话执行完请书记员归档；执行方是研究员的，留在视图里，研究员做完说一声再归档。

## 老空间补到 2.2.0

用 2.1.0 及以前的模板建的空间，可以照[搭建手册.md](搭建手册.md)补到和 2.2.0 一致：第 2 节加“执行方”“研究员要做的事”两个字段，第 4 节把状态“已决定”改名“待执行”，第 6 节配详情页、表格列和“待定决策”视图。不补也能用插件 1.0.5 及以后的版本，只是没有这个视图和两个字段。

空间补完，已经绑定它的项目还要做一步，插件才认得，按补了什么分：

| 在空间里补了什么 | 项目里要做的一步 | 谁做 | 不做会怎样 |
| --- | --- | --- | --- |
| 只加两个字段（第 2 节），配详情页、表格列和视图（第 6 节），状态没改名（视图筛选里的“待执行”选“已决定”） | 重读一次空间结构的快照：`python3.12 -I .claude/solo-lab/bin/space.py snapshot --target . --apply` | 任何会话 | 台账在快照里找不到这两个字段，登记和修订决策时照旧不写它们，视图里这两列是空的 |
| 把状态“已决定”改名“待执行”（第 4 节），不管另外补没补字段 | 重新绑定：`space.py feishu --target <项目目录> --live`，核对后加 `--apply`。它同时重读快照，上一行那一步不用另做 | 研究员的会话 | 台账还按“已决定”查：`ledger.py query queue` 列不出待执行的决策，确认“决定”以后不打印执行方，研究任务的签字核对认不出已经决定的决策 |

两个字段不是约定里的槽位，插件按名字在快照（`feishu/space.json`）里找，不用重新绑定。状态是槽位，名字记在绑定（`feishu/ids.json`）里，只重读快照改不了它；重新绑定时先认标识，改了名照样对得上，换的只是名字。视图、详情页和表格列插件不读，不用做什么。做完在项目目录里核对：

```bash
python3.12 -I .claude/solo-lab/bin/space.py check --target .
```

状态改了名、还没重新绑定时，它报“空间里现在是 “待执行”，绑定记的是 “已决定””。升级前登记、还没归档的决策，这两个字段是空的；要补的，书记员照回执用 `workitem.py update` 补，做法见插件的 `skills/setup/references/mechanisms.md`“升到 1.0.5”一条。

## 老空间补到 1.1.0

1.1.0 只改名字，一共 18 处，都在研究任务这一类上，清单见[更新记录.md](更新记录.md)。用 2.2.0 建的空间照清单在空间配置里逐个改名，都在原对象上改，不新建也不删除。改名和插件升到 1.1.0 放在同一次做：研究任务单开头的“流程”一行要和空间里的流程名一字不差。改完以后任何会话重读一次空间结构的快照：`python3.12 -I .claude/solo-lab/bin/space.py snapshot --target . --apply`。

在途的工作项不要点“模板升级”。它们的节点名一直显示旧名字，流程名、状态、字段和选项显示新名字，照常能往下走；任务单开头“流程”一行还写着旧名字的，下一次修订时改成新名字。

## 模板和插件怎么对接

| 层 | 内容 | 在哪里 |
| --- | --- | --- |
| 约定 | 脚本按含义处理的槽位：5 个类型，19 个字段，9 个角色，各类型要有的状态，以及签字关、方案关和归档节点的规则 | 插件的 `orgspec/contract.json` |
| 绑定 | 每个槽位对应这个空间里的哪个类型、字段、角色和状态 | 项目的 `feishu/ids.json`，初始化时生成 |
| 流程和表单 | 有哪些流程、节点怎么排、谁负责、必填什么 | 只在飞书空间里，插件运行时读 |

槽位以外的字段，插件按名字读写。模板加字段、改流程、改必填项而槽位都在时，插件不用改。

绑定先认标识，再认名字：类型认系统标识，角色认角色 id，字段认对接标识，都对不上才按名字找。命令行只读得到新建页上那些字段的对接标识，其余字段按名字绑定。照[结构.md](结构.md)里的标识搭出来的空间，绑定不用人工指认。

## 核对一个空间

```bash
python3.12 -I plugins/solo-lab/scripts/space.py check --space <空间名、simple_name 或 project_key>
```

这条命令只读飞书，不写文件。它读出空间的结构，逐个槽位找对应的对象，再核对流程：每个流程正好一个末尾节点且由书记员负责，每个节点正好一个约定里的角色，签字字段和结论字段在某个节点上是必填。退出码 0 是通过，1 是有缺项，缺项逐条列出。

流程图只能从一条工作项读出来。某个流程还没有工作项时，命令提醒读不到这个流程，其余照常核对。

## 改模板

1. 在模板空间里改配置。
2. 每个改过的流程用一条工作项从第一个节点走到“归档”，再回滚一次。
3. 跑上面的核对命令，通过后把结构快照读到一个临时文件，再从它生成[结构.md](结构.md)。快照文件里有空间的各种标识，不放进仓库：

```bash
python3.12 -I plugins/solo-lab/scripts/space.py export --space <模板空间的名字> --out <space.json>
```

```bash
python3.12 -I plugins/solo-lab/scripts/space.py show --snapshot <space.json> structure
```

4. 在网页上删掉第 2 步的样例工作项：工作项详情页右上角的“···”里有“删除”。命令行删不了。
5. 发布为模板：模板中心 → 我的模板。“编辑数据”一步里，决策的视图和空间置顶都选“全部上传”，工作项实例不上传。把版本、日期和改动写进[更新记录.md](更新记录.md)。

## 版本规则

从 1.1.0 起，模板的版本号和插件对齐（研究员 2026-11-21 定）：模板有改动时，和插件的一次发版一起发布，用那一版插件的版本号。插件发版而模板没有改动时，模板不重新发布，版本号不动。所以模板的版本号说的是插件从哪一版起用它。1.1.0 以前模板自己编号，2.0.0 到 2.2.0 是那时的版本。

| 改了什么 | 怎么发布 |
| --- | --- |
| 符合的 `contract_version` 变了（槽位增减） | 另建模板空间，发成新模板，链接换新 |
| 流程、节点、状态、字段或选项改了名，或者别的改动让旧版插件用不了 | 发成新模板，链接换新；旧模板和旧链接原样留给旧版插件 |
| 其余改动，旧版插件照样能用 | 在原模板上重新发布，链接不变 |
