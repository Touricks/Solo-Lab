# 前置检查和登录

## 脚本查的项

`setup.py precheck` 逐项打印“通过、提醒、失败、跳过”，有失败项时最后一行是“预检：N 项失败。”，退出码是 1。失败项先处理。要升级、要改配置的，把命令给研究员，由他本人在终端里执行；登录由初始化会话发起，研究员扫码。

| 项 | 查什么 | 没通过时 |
| --- | --- | --- |
| 飞书客户端 | macOS 上有没有 Lark.app 或 Feishu.app | 只是提醒：网页版也能用 |
| lark-cli 版本 | `lark-cli --version` 不低于 1.0.96 | 研究员本人运行 `lark-cli update` 升级。它会在 `~/.claude/skills/` 下建一批软链接，先告诉研究员 |
| meegle 版本 | `meegle version` 不低于 1.0.23 | 研究员本人按官方安装说明用 npm 全局升级 |
| claude 版本 | `claude --version` 不低于 2.1.219 | 版本低于下限报失败：升级 Claude Code。找不到 `claude` 这条命令只是提醒：只装了桌面应用时没有它，不影响初始化 |
| lark-cli doctor | 配置文件、应用、机器人和用户身份、开放平台连通性 | 看它列出的没通过的检查项。是用户身份的，照下面“登录”处理 |
| lark-cli 用户身份 | `lark-cli auth status` 里用户身份可用。访问令牌过期、续期凭证还有效也算通过：下一次调用会自动续期 | 照下面“登录”处理 |
| meegle 登录 | `meegle auth status` 退出码为 0 | 照下面“登录”处理 |
| 飞书项目权限 | `meegle project search` 能看到至少一个空间 | 一个空间都看不到只是提醒：初始化会用模板建出项目空间，接着做。说明写着“输出不是 JSON”的才是失败，先看 meegle 版本和 meegle 登录这两项 |
| meegle 诊断上报 | `meegle telemetry status` | 开着时提醒研究员决定是否关闭；`meegle telemetry disable` 由研究员本人执行 |
| 飞书私聊事件订阅 | `lark-cli event consume im.message.receive_v1 --as bot --dry-run`：凭证、开发者后台已发布事件订阅、权限 `im:message.p2p_msg:readonly` | 只是提醒：没就绪时入口收不到飞书私聊，研究员转述也行。要用的话请应用管理员在开发者后台开事件订阅和权限 |
| Python | 3.9 以上，脚本只用标准库 | 升级 Python |
| 技能 lark-doc、lark-wiki、meegle | `~/.claude/skills` 或 `~/.agents/skills` 下有没有 | 只是提醒：书记员用 `ledger.py`，不依赖它们，人工排查时有用 |

三个版本下限写在 `setup.py` 的 `MIN_VERSIONS` 里，以它为准。

## 脚本查不了、会话自己确认的

- **运行环境。** 本会话有没有开会话的工具 `start_session` 和给别的会话发消息的工具。没有就停下，说明这一版只支持 Claude 桌面端。
- **界面操作的工具。** 项目空间不存在时才用得到，到那一步再看，顺序见 `create-space.md`。
- **建空间的权限。** 研究员的账号要能在飞书项目里用模板创建空间。建空间的人就是空间管理员。脚本查不了这一项，创建失败时才知道。

## 登录

登录只有一个入口，由初始化会话运行：

```bash
python3 -I "$PLUGIN/scripts/setup.py" login
```

- 它先查两种命令行的登录状态，给登录失效的那个发起设备码登录。两个都有效时打印“lark-cli 和 meegle 都已登录，不用再登录。”。
- 每个要登录的命令行打印三行：多久内有效、二维码图片的路径、链接。会话把图片和链接交给研究员，研究员扫码或打开链接授权。
- 二维码图片和等待中的登录记录放在 `/tmp/agent-org-login-<用户号>/` 下，目录只有本人能读写，登录结束就删。设备码只在这个记录里，不打印。会话不接触密码、验证码和令牌。

研究员授权以后读回状态：

```bash
python3 -I "$PLUGIN/scripts/setup.py" login --wait
```

| 输出 | 意思 |
| --- | --- |
| “<命令行>：已登录。” | 登录成功 |
| “<命令行>：还没授权，二维码还有 N 分钟有效；研究员授权以后再运行 setup.py login --wait。” | 研究员还没扫，退出码 1 |
| “<命令行>：授权超时，这次的二维码作废；重新运行 setup.py login。” | 二维码过期，退出码 1 |
| “没有在等的登录：先运行 setup.py login。” | 没有发起过，或者已经读回过了，退出码 2 |

- `--wait` 默认最多等 300 秒，`--timeout <秒数>` 可以改。没等到就再运行一次，二维码有效期内都能接着等。
- 设备码登录由会话发起、研究员扫码完成，这条路没有在真实初始化里走完过。发起失败时脚本报“…的设备码登录没发起成…”：这个命令行的登录请研究员在自己的终端里做，做完重跑前置检查。
- 角色会话不发起登录。它运行 `setup.py login` 会被 hook 拒绝，理由是“登录由研究员的会话发起（setup.py login），研究员扫码完成：把“登录过期”报给研究员。”。
- 会话不直接运行命令行自己的登录、登出命令，也不改它们的配置和诊断上报设置：项目权限和 hook 都拒绝。
