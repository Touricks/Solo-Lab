# 组织设计怎样落到 Claude 桌面端

运行方式只有一种：会话池。每个角色是研究员在桌面应用侧栏里看得见的一个会话，派活、交回、登记都是会话之间的消息。

## 生成的目录

```text
<项目目录>/
├─ CLAUDE.md                     所有会话都要知道的：研究任务、职级、交接规则、命名、东西在哪、运行机制
├─ agent-org.task.json           任务文件，初始化会话写的；改设置就改它，再重跑 init
├─ .env                          飞书项目和知识空间的两行链接
├─ .claude/
│  ├─ settings.json              权限（allow、ask、deny）和 hook 注册
│  ├─ agents/                    21 份角色定义：七个序列各三级；项目管理的 +1、+0 是 pmo-router、pmo-scribe
│  ├─ hooks/                     guard、audit、instances、inbox、feishu_cmd、pool，和它们读的 policy.json、lark-risk.json
│  ├─ agent-org/
│  │  ├─ bin/                    orgspec.py、ledger.py、route.py、space.py、pool.py、project_paths.py、onboarding.py
│  │  ├─ orgspec/                规则文件、术语表和约定文件的副本
│  │  ├─ templates/              三种包的模板副本
│  │  ├─ pool-plan.json          开池清单：每个会话的标题、模型、开局句和预登记命令
│  │  └─ manifest.json           插件版本、启用的序列、规则、术语表和约定文件的哈希、每个生成文件的哈希
│  ├─ state/                     pool.json（认领表）、sessions/（各会话的状态）、onboarding.json（初始化计时）
│  └─ logs/                      guard.jsonl（hook 的判断和提醒）、dispatch.jsonl（消息和认领）、compact/（压缩摘要）
├─ org/                          org.md（组织规则全文）、grants.md（授权表）、decisions.md、phases.md（研究任务的流程）
├─ packages/drafts/<序列>/       任务包草稿；drafts/pmo/ 里有首条研究任务单；packages/sent/ 是书记员的登记回执
├─ inbox/                        各会话的收件箱、飞书私聊消息
├─ spec/                         实验规格、评测协议、需求文档的草稿，和 task.json
├─ feishu/                       ids.json（绑定）、space.json 和 space.md（空间结构）、binding.md、写操作日志
└─ runs/                         运行记录
```

- 已有文件分三种处理。上次生成后没人改过的直接更新；本地改过的，新版本写在旁边的 `.new`，由研究员对照合并；`org/decisions.md`、`org/phases.md`、`spec/` 下的三份文档和首条研究任务单归研究员和各角色维护，建好以后 `init` 不再动。
- `spec/task.json` 跟着 `init --task` 给的任务文件走。会话改不了它：要改设置，改任务文件再重跑 `init --apply`。
- 21 份角色定义不用来派子智能体。会话认领角色以后，hook 把对应的那份注入会话，当它的工作说明。
- `guard.py` 和 `policy.json` 要成对更新。两个都写成 `.new` 时一起合并，再重跑 `init`。

## 对照表

| 组织设计 | 在本插件里怎么做 | 依据和局限 |
| --- | --- | --- |
| 项目管理 +2 是研究员平时的入口 | 认领了 pmo-p2 的会话 `PMO-p2-01` | 入口长期运行，上下文会被压缩，所以它每次从台账、状态包和 `route.py pool` 读状态。研究员特殊情况下直接点开其余六个 +2 的会话，谈定的事仍写成决策包交给入口 |
| +2 → +1 → +0 逐级派发 | 入口给各序列 +2 的会话发消息，+2 给本序列 +1 发，+1 给本序列 +0 发。消息首行写抬头，正文在包文件里 | 派发图写在规则文件的 `dispatch` 一节。这是规范：对不上派发图的消息，收方的 hook 只提醒、记日志 |
| 跨序列只在 +2 之间 | +1、+0 要别的序列配合，写进交给上一级的交付包，由本序列 +2 发跨序列的需求包，经入口转交 | |
| 书记员是台账和文档唯一的写入方 | meegle 和 lark-cli 的写命令、`ledger.py` 的写子命令只放行唯一认领的书记员会话；其他会话只能加带标签的评论。`ledger.py --apply` 还加文件锁，同一时间只有一个写入 | 所有会话用的是研究员一个飞书账号，飞书分不出是哪个会话，只能靠 hook 分权。hook 是防误操作的护栏：它按命令文本判断，刻意混淆的命令藏得过去，真正的边界是研究员账号的权限 |
| 派 +1、+0 之前要有工作项 | +2、+1 把草稿交给书记员登记，拿到工作项 ID 再派。登记请求写了“开工”的，书记员登记后接着确认“开工”这一步 | 排队没派的留在“待开工” |
| 会话名和会话标签 | 会话名在开局句里，写作 `Alg-p2-01` 这样的池位名。+0 干活时另有派活消息给的工作名 `Alg-p0-<工作项 ID>`。“负责会话”字段约定记池位名：需求包包头的接收方写了它就记它，没写才记工作名，脚本两个都认 | |
| 并行上限 | 每个序列 +2 一个、+1 最多三个、+0 最多五个会话，入口、路由、书记员各一个。任务文件的 `pool.max_sessions` 是全池的总上限 | 到了上限，`route.py expect` 拒绝预登记 |
| 研究员直接委托某个 +2 | 研究员点开那个会话，它运行 `route.py focus open` 标成“研究员在用”，`route.py pool` 这期间不推荐它 | 空闲 30 分钟后标记自动失效 |
| 不打断正在被研究员用的会话 | 用 `route.py notify` 写进它的收件箱，它下一轮开始时 hook 把未读消息加进上下文 | |
| 研究员在飞书私聊里发消息 | `route.py listen` 订阅机器人收到的私聊，写进 `inbox/feishu.jsonl`，入口下一轮看到 | 要研究员本人在终端里启动。`feishu/ids.json` 里没有研究员的 open_id 时不启动 |
| 没写进台账的决定不算数 | 研究员当面谈定的事写成决策包，渠道写“研究员主动发起”，书记员登记后接着确认“决定”这一步 | 靠规则和入口的收尾步骤保证，hook 拦不住口头决定 |
| 评测协议只读，可改范围只给工程 | hook 按任务文件的路径管写入：`protected_paths` 除质量序列外一律拒绝，质量序列也要研究员确认；`editable_paths` 照规范只给工程序列，别人改了 hook 提醒 | 只管 Claude 的文件工具。脚本在 shell 里写文件，要靠运行环境的只读挂载；项目目录以外的评测数据 hook 管不到 |

| 身份 | 知识库、文档、云空间的命令显式带 `--as user`，收发消息带 `--as bot` | |
| 写操作留痕 | 直接调用的写命令由 `audit.py` 记日志，`ledger.py` 自己记 | 都写进 `feishu/write-log.jsonl` |
| 插件自己的脚本 | hook 只信任 `.claude/agent-org/bin/` 下、内容和 manifest 哈希一致的脚本。改过的脚本里调用飞书命令行，一律按看不见的命令拦下 | 插件目录里的 `setup.py` 不在信任范围内。研究员的会话运行它，hook 读得到文件时会询问，bypass 和 dontAsk 模式下直接拒绝 |
| 跨阶段的记忆 | 各序列 +2 在 `.claude/agent-memory/<角色>/` 记要沿用的标准和判断 | 任务状态以台账和状态包为准 |

## 会话池

- **开池。** 会话按派活的方向一层开一层：做初始化的那个会话照 `setup.py pool` 的清单分批开出七个 +2，每个开出来先用 `detach_session` 移到顶层（和它自己同级），再用 `route.py expect` 预登记；+2 在首轮里开出本序列的 +1，+1 在首轮里开出 +0，入口下面是路由，路由下面是书记员。分批是因为应用有上限：会话自己开出的会话同时最多 5 个在跑，所有序列合在一起算，+2 移到顶层也不分开算；一批下面要开的会话不超过 4 个，默认分 3 批。应用还有一条总数上限：研究员每发一条消息以后，这样开出的会话最多 10 个。所以批再分成轮，一轮下面要开的不超过 8 个，默认 2 轮；一轮开完，做初始化的会话停下，请研究员回一句“继续开池”，再开下一轮。下面两级不归做初始化的会话管，它用 `setup.py pool --wait <秒数> --batch <第几批>` 等一批认领完、首轮都结束，再开下一批；最后用不带 `--batch` 的 `--wait` 等到清单里的会话都认领、书记员的首轮结束，没等到就列出还差谁、该由谁开。桌面端把一个会话嵌在开出它的会话下面，所以侧栏里是 +2、+1、+0 三层。默认 19 个：七个 +2、路由、书记员，外联以外的五个序列各一个 +1 和一个 +0。做初始化的会话开不了会话时走回退档：研究员手工新建七个 +2 会话，各粘贴一句开局句，往下的开法相同。被别的会话的消息叫起来的那一轮，桌面端不让开会话：下一级没开出来，或者以后要“补位”，都要研究员在上一级的会话里亲口说。
- **标题和分区。** 会话标题是 `[<飞书项目空间名>] <会话名>`，任务文件的 `pool.label` 可以另指前缀。会话都归入同名的侧栏分区，不置顶。做初始化的那个会话标题是 `[<名字>] Initialization`，它不是入口。标题只用来看，预登记和认领不依赖它。
- **认领。** 会话靠认领成为某个角色，认领要有许可。许可有两种：开局第一句“认领 <角色>（会话名 <名字>）”，只认 +2；或者开它的会话用 `route.py expect` 做的预登记。研究员的会话可以给任何角色预登记，+2 只能给本序列的 +1、+0，入口只能给路由和书记员。hook 把许可转正成认领，`route.py` 自己不写已转正的认领。认领表在 `.claude/state/pool.json`，`guard.py` 拦对它的编辑。
- **角色说明。** 认领后 hook 把角色定义注入会话；压缩、恢复、清空上下文以后再注入一次，带上未了事项。
- **认身份。** hook 先看调用是不是子智能体，再按会话 ID 找认领，再找许可。按桌面会话 ID 找到的认领，只有原来的会话因为清空上下文而结束、新会话是清空以后开局的，才接到新会话上。从池会话里起的进程带着同一个桌面会话 ID，不算这个角色，没有写权。都没有的是研究员自己的会话，它没有任何角色的写权。
- **工作目录。** 每个会话都在项目目录里开，不开 worktree。hook 在会话开始时记下工作目录，`setup.py check` 核对它等于项目目录。
- **派活。** 给对方的会话发消息，不用 Agent 工具派组织角色。先运行 `route.py pool --role <角色>` 找空闲的会话；没有空闲的就排队，活留在台账的“待开工”。消息首行写抬头，比如 `【派活 #2101】Alg-p2-01 → Alg-p1-01：需求包 <路径>`。收方的 hook 把收到的时间记进 `.claude/logs/dispatch.jsonl`，这就是回执。
- **状态。** 每个会话的 hook 维护自己的状态文件：在忙、空闲、后台任务在跑、等研究员批准、失败、离线。`route.py pool` 汇总，`--watch` 每 30 秒刷新，`--recover` 在重启后列出要接着做的事。
- **权限模式。** 全池和研究员的会话用同一类：bypass 和其他模式之间，会话的消息会被扣下。hook 记下每个会话的模式，`route.py pool` 和 `setup.py check` 标出不同类的。bypass 和 dontAsk 模式下，hook 本该弹窗询问的一律换成拒绝，理由里写“请研究员在自己的终端里运行”。 开池用 auto 模式：四轮现场测试都是 auto 模式，开会话不用研究员点。bypass 模式下，应用对每一次开会话都弹一张确认卡，只有 Deny 和 Allow once，弹在发起的那个会话里，+2 开 +1、+1 开 +0 也一样，默认的 19 个会话要点 19 次；这是应用有意留的确认，hook 放行也跳不过，插件不去绕开。`setup.py pool` 开池前读本会话的模式，是 bypass 就先提醒。

hook 只拦会损坏数据的事，其余是规范，`route.py audit` 汇总提醒：

| 哪些会话 | hook 怎么办 | 管什么 |
| --- | --- | --- |
| 任何会话 | 直接拒绝 | 改 `.claude/` 下的 hook、配置、角色定义和认领表；改评测协议的只读路径，质量序列的会话例外，它的改动要研究员确认；high-risk-write 和带 `--yes` 的飞书命令；派发时带 `name`；用 Agent 工具派书记员；不照规定写法的认领、预登记和释放；第二条入口或书记员认领 |
| 研究员的会话询问，别的会话拒绝 | 弹窗或拒绝 | 书记员以外的会话写飞书和台账；在共享工作区里切分支、stash、reset 或 pull；释放认领 |
| 角色会话 | 拒绝 | 运行 `setup.py login`：登录由研究员的会话发起 |

Monitor 工具和终端面板里运行的命令，和 Bash 一样检查。

### 开池以后

- **补位。** 会话一层开一层，补位也一样：要多开 +1，研究员在那个序列 +2 的会话里说“补位”或“再开一个 alg-p1”；要多开 +0，在它上面那个 +1 的会话里说。那一轮里这个会话照认领输出里“补位用”的那一行开会话并预登记，新会话在侧栏里嵌在它下面。开池时只开了 +2 的序列，在它的 +2 会话里说一句“补位”：+2 开出 +1，+1 在首轮里接着开出 +0。路由由入口开，书记员由路由开。没人要求时会话不自己开，只用 `route.py refill <角色>` 记一条补位请求，进入口的每日决策队列。
- **某个会话丢了。** 研究员先运行 `route.py release <会话名>` 释放旧的认领，再回到研究员的会话，照 `setup.py pool` 的清单把它重新开出来，清单里它显示“未认领”。回退档里丢的是 +2 的，研究员新建一个顶层会话，粘贴 `pool-plan.json` 里它的 `rebuild` 句。
- **重启或电脑睡眠以后。** 研究员对入口说“恢复”，入口照 `route.py pool --recover` 的清单逐个续上，书记员先补完写到一半的登记。
- **升级插件。** 在研究员的会话里重跑 `init --apply`，研究员退出并重开桌面应用，各会话下一轮开始时由 hook 注入新的角色说明。`setup.py check` 会列出还停在旧版规则上的会话。
- **收掉会话。** 会话不去归档、清空或停止别的池会话。要收掉，由研究员本人在侧栏操作，再 `route.py release`。归档一个会话，嵌在它下面的会话跟着一起归档：归档 +2 会带走本序列的 +1 和 +0，只想收掉 +2 时先在侧栏里把它下面的会话移到顶层。

## 把关靠测量

没有送审这一环。Eval Set 和阈值在出结果之前定下，研究员在验证流程第 4 步签字后冻结；正式分数只由质量序列在冻结的 Eval Set 上跑出，执行方自己跑的是开发分；结论只对照签过字的阈值。书记员确认节点前，脚本核对三样：是谁提的请求，签字字段引用的决策合不合格，冻结的字段在签字后有没有被改过。

## 待实测的假设

这一版做过五轮初始化的现场测试和一次六个流程的测试，逐项的记录在插件仓库的 `docs/Claude实测记录.md`。下表最后一栏是到 2026-11-13 为止的结果；没验证的，技能里涉及它们的步骤都写了不成立时怎么办。

| 编号 | 假设 | 不成立时 | 实测 |
| --- | --- | --- | --- |
| P1 | 桌面会话的 hook 环境里有桌面会话 ID，子会话的第一个 hook 事件就能按预登记转正 | 子会话运行 `route.py claim`，由 `audit.py` 在这条命令结束时转正；清空上下文以后按时间配对接回 | 成立：四轮里开出的会话都按预登记转正 |
| P2 | 开局 prompt 和别的会话发来的消息会触发收方的 hook | 收到的记录改由发方记；提醒改在收方第一次调用工具时附上 | 成立：派发日志里有收方的记录 |
| P3 | 同一类权限模式的会话之间，消息能送达，对方随即开始一轮 | 派活改成收件箱留言，研究员点开对方会话；还不行就停下，报给研究员 | 成立：六个流程的测试里发了 114 条消息，收方都接着做了 |
| P4 | Auto 模式下，由别的会话来信开始的轮次里，派活、写台账、改文件不被拦 | 池的常用命令已写进精确的 allow；仍被拦的改由研究员在场时做，或换权限模式 | 成立：hook 记下前四轮和六个流程的测试都是 auto 模式，114 条消息和 9 条工作项都走完了 |
| P5 | 开会话时 model 填 opus、sonnet、haiku 这样的别名能生效 | 不填，开好以后再改模型 | 没有记录 |
| P6 | 二十个左右的会话同时开着，本机内存够用 | 调小任务文件的 `pool.max_sessions`，用 `pool.later` 推迟不急的序列 | 没有记录 |
