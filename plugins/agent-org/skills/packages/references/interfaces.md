# 跨序列接口

跨序列的任务包只在 +2 之间交接。下表是七个序列之间约定的主要接口；表里没有的交接，按 `../assets/request.md` 的跨序列关系写，承接方在跨序列需求的“接单”这一步确认。

## 跨序列的需求包和交付包

| 发起方 +2 | 承接方 +2 | 需求包交接什么 | 交付包交付什么 | 典型触发 |
| --- | --- | --- | --- | --- |
| 产品 | 算法 | 需求文档里约束规格的判据、成功阈值、停止条件 | 签字后的规格，逐条对应判据；或者指出冲突 | 需求文档定稿后，第 4 步签字之前 |
| 产品 | 质量 | 要建的 Eval Set、评测协议的要求 | Eval Set 的版本和评测协议 | 验证流程第 3 步 |
| 算法 | 质量 | 规格里要核对的假设、阈值和波动估计 | 阈值核对的结果 | 验证流程第 4 步，签字之前 |
| 工程 | 质量 | 要出正式分的结果，附运行 ID 和试过的变体数 | 正式分和每次打分的运行 ID | 验证流程第 7 步，一轮实验跑完 |
| 算法 | 工程 | 搜索流程、运行记录格式、重复次数 | 可重放的实验流程、运行记录样例；实现和规格的偏差 | 规格签字、实验方案定了以后 |
| 算法 | 基础设施 | 运行环境要强制执行的约束：评测协议只读、实验资源的计时范围、外层看不到测试集 | 已就绪的资源和环境；约束有效性的测试结果 | 规格或评测协议签字、改版后 |
| 工程 | 基础设施 | 新增的资源、挂载和工具能力 | 已就绪的环境 | 实现需要新能力时 |
| 质量 | 发现问题的那个序列 | 审计里发现的问题和后续要求，比如规格修订 | 修订结果，以及受影响结果的处理办法 | 审计 Eval Set 和打分脚本发现问题时 |
| 项目管理 | 外联 | 研究员要的周报、月报或别的对外材料：目的、读者、时间范围 | 写好的材料，发出前由研究员签字 | 研究员对入口说一句 |
| 外联 | 项目管理 | 材料要用的台账查询和字段 | 生效的查询和字段 | 材料模板调整时 |
| 基础设施 | 项目管理 | 预检要读取的工作项字段 | 生效的字段 | 预检清单调整时 |
| 任一序列 | 项目管理 | 新字段、新模板、新的台账查询 | 生效的改动 | 本序列的工作方式变化时 |

## 质量序列的接口

把关靠管住测量：Eval Set 和阈值在出结果之前定下，正式分数只由质量序列跑出。质量序列在验证流程里承接三次跨序列的需求包，另外自己做审计。

| 什么时候 | 谁发需求包 | 质量序列做什么 | 交回什么 |
| --- | --- | --- | --- |
| 第 3 步 准备 PRD 和 Eval Set | 产品 +2 | 建并冻结 Eval Set，分开发集和正式集；写评测协议 | Eval Set 的版本和评测协议 |
| 第 4 步 确定假设条件 | 算法 +2 | 核对规格里的假设和阈值 | 阈值核对的结果 |
| 第 7 步 跑 Eval Set | 工程 +2 | 在冻结的 Eval Set 上出正式分 | 正式分和每次打分的运行 ID |
| 平时 | 质量序列自己 | 审计 Eval Set 和打分脚本，查数据泄漏和打分脚本漏洞 | 发现问题时，向出问题的那个序列的 +2 发跨序列的需求包 |

- 正式集只由质量序列持有，每一轮只跑一次。执行方只碰开发集，自己跑出的是开发分，只用来调试，不写进结论。
- 结论由负责“得出结论”这一步的序列对照签过字的阈值写，成立、不成立、无法判定三选一。质量序列出分数，不逐份审别的序列的结论。
- 只有质量序列能改评测协议的只读路径，改动要研究员确认。评测协议和证据标准要变更，质量 +2 写决策包请研究员签字。
- 质量序列和别的序列有争议，质量 +2 写决策包请研究员裁决。

## 项目管理和外联的接口

| | 项目管理 | 外联 |
| --- | --- | --- |
| 管什么 | 流转、台账、决策队列，反馈的登记和解析 | 写给研究员以外的读者看的材料：周报、月报、决策备忘，论文和合作人材料的润色 |
| 读者 | 研究员和组织里的会话 | 导师、合作人这些研究员以外的读者 |
| 写不写内容 | 入口、路由、书记员三个会话都不写内容；任务包、材料和结论由各序列写，书记员只把它们存进飞书 | 写材料；每份发出前研究员签字，走决策包 |

- 一件事归不归外联，只看读者：读者是研究员本人或组织里的会话，就不归外联。
- 导师意见的登记和解析、对导师承诺的跟踪归项目管理；外联写材料时从台账读。
- 材料不按固定时间出。研究员对入口说一句，入口给外联 +2 发跨序列的需求包，不设定时任务。
- 外联只读台账，不向其他序列发需求包索要结论；要写进材料的结论还没有正式分时，在交付包里上报。

## 不走任务包的交接

- 资源和工具声明：工程 +1 请书记员写进工作项，基础设施预检时读取。用哪个字段看 `feishu/space.md`；空间里没有对应字段时，写成带会话标签的评论。
- 开工预检记录：基础设施写成工作项评论。
- 节点的确认和回滚：负责这一步的会话给书记员发登记请求。
- 信息路由：项目管理的路由把新信息送到受影响的会话；由此产生的新任务，经 +3 决定后交给对应序列的 +2。
- +3 的指示：经项目管理登记成工作项，交给对应序列的 +2。
- 反馈：入口请书记员把原话登记成反馈工作项并解析；拆出的事项经研究员确认后，才由对应序列的 +2 写成包。

## 约束谁的规则，不经谁转交

约束某个序列的规则，不经由这个序列转交。工程受评测协议和实验资源的约束，所以这两条约束由算法 +2 直接交给基础设施 +2。
