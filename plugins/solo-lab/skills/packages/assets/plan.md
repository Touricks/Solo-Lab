# 方案模板（下发的需求：承接的 +0 → 本序列 +2）

下发关系的需求包只定目标、验收标准和授权范围，做法由承接的 +0 定。动手之前先把做法写成方案交给发出方，它在同序列需求的“定方案”这一步确认，确认以后才执行。方案不是任务包：不建工作项，不过包检查；它挂在那条需求的主文档下面，链接填在工作项的“方案”字段里。

| 谁 | 做什么 |
| --- | --- |
| 承接的 +0 | 照下面的模板写，运行 `docs.py attach <工作项 ID> 方案 <方案文件> --apply` 自己上传，再用【通知 #ID】把文件路径告诉发出方 |
| 发出方 +2 | 对照需求包看三件事：照这个做法能不能达到验收标准，拆出去的子任务是不是封闭任务，资源够不够。可以，就请书记员确认“定方案”（必填项写 `方案=@<方案文件>`），再用【继续 #ID】告诉 +0 动手；要改，告诉它改什么，不确认 |
| 书记员 | 确认“定方案”这一步，把方案的链接填进“方案”字段 |

方案写什么，各序列不一样：工程写架构方案，基础设施写实验环境的维护方案，质量写测试集的划分方案，算法写实验方案，产品写调研方案，外联写材料的提纲。每个序列要写清的几项，在 `org/org.md` 里本序列 +0 的那一行，也在你的角色说明里。

## 模板

```markdown
# 方案：<任务名称>

- 关联工作项：#<下发需求的工作项 ID>
- 作者：<序列> +0（会话名）
- 版本：第 1 版（<YYYY-MM-DD>）

## 对需求的理解
<用自己的话写要做成什么、怎么算做成。需求包里有两种读法的地方写在这里，发出方确认方案时一起答。>

## 做法
<照本序列的方案要点写，写到发出方能判断“照这个做，验收标准能不能达到”为止。>

## 拆分
<要派给本序列别的 +0 的封闭子任务，一条一行：做什么、验收标准、会改哪些文件。不拆写“无”。>

## 资源和期限
- 预计用多少：
- 什么时候交：

## 不做的事和风险
<这次不做什么；哪一步最可能走不通，走不通怎么办。>
```

## 填写规则

- 方案确认以前不动手。读代码、查资料、试一个最小的例子可以；花算力、改共享文件、派子任务不行。
- “做法”写到能判断为止，不写成操作手册。写不出来，多半是需求包的目标或验收标准没说清，先问发出方。
- 拆出去的子任务要是封闭任务：做到一半不需要新的信息或新的判断。要判断的部分自己做。子任务用执行关系的需求包派，上传时写 `--source <这条需求的工作项 ID>`；交付由你验收，结论汇总进你的交付包的“子任务汇总”一节。
- 方案确认以后不再改这份文档。范围内的调整自己定，记进交付包的“和方案的出入”一节。要改目标、改验收标准、超出资源上限或者超出方案的，停下来告诉发出方；它同意了，你写下一版（版本号加 1）重新上传，它请书记员把“方案”字段换成新的链接。
- 做不到也写成方案：写明缺什么、建议怎么办。发出方据此改需求，或者向研究员提决策。

## 示例：产品 +0 交的调研方案

需求是 `references/examples.md` 里的第一份包（#2001，代码优化器的需求文档）。

```markdown
# 方案：代码优化器的需求文档

- 关联工作项：#2001
- 作者：产品 +0（Product-p0-2001）
- 版本：第 1 版（2026-10-20）

## 对需求的理解
要交一份能签字的需求文档，回答两件事：代码优化器值不值得做，做成了算什么。验收标准第 2 条“现状基线有实验日志或访谈记录支撑”，我理解成两样都要有：日志给数字，访谈解释数字。

## 做法
- 调研对象：推荐团队做模型迭代的四位工程师。
- 要收集的字段：每周试几个改动、一个改动从想到合入要多久、卡在哪一步。
- 访谈提纲：先问最近一次没合入的改动，再问评审时看什么。
- 现状基线：统计上季度实验日志里每周的改动次数，访谈里核对。
- 试点：两位工程师用四周，看他们会不会不经提醒就用。

## 拆分
- 统计上季度实验日志里每周的改动次数：给出按周的表和脚本；只读 runs/product/evidence/ 以外的日志，不改文件。

## 资源和期限
- 预计用多少：访谈三次，每次一小时。
- 什么时候交：两周内。

## 不做的事和风险
不评估优化器的算法怎么做。风险：工程师排不出时间，访谈可能只做成两次；两次够问完提纲就不补第三次。
```
