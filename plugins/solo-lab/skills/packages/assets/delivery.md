# 交付包模板（需求包的接收方 → 发出方）

接收方答复需求包，关系和所答复的需求包相同。交代多少，和委托时给了多少自主权对应：执行关系只交对照结果和异常；下发关系还要交代结论为什么成立、判断变了什么、授权内做了哪些决定、哪些事要 +1 决定，再加上和方案的出入、子任务的汇总；跨序列关系交付时写判断的变化、偏差和使用限制。

| 关系 | 发出方 → 接收方 | 需要接收方做的事 | 存放 |
| --- | --- | --- | --- |
| 执行 | 本序列 +0 → 派活的会话 | 确认完成 | 挂在需求包下面；没有工作项，派活的会话用 `docs.py accept` 验收 |
| 下发 | 本序列 +0 → +1 | 决定下一步：继续、转向、停止，或者向其他序列和研究员提出需求 | 挂在需求包的主文档下，链接写进同序列需求工作项的“交付包”字段 |
| 跨序列 | 承接方 +1 → 发起方 +1 | 接收交付 | 挂在需求包的主文档下，链接写进跨序列需求工作项的“交付包”字段 |

交付包里的结论对照验收标准写，证据列全：材料来源、每个变体的结果和运行 ID，失败的也列。实验方自己跑出的分数是开发分，只用来调试；要写进研究任务结论的正式分，只由质量序列在冻结的 Eval Set 上跑出。

跨序列关系的接单不写交付包：承接方 +1 把对需求的逐条复述、承接范围和预计交付时间写进登记请求发给书记员，书记员确认“接单”这一步时填进去；确认以后把这三项直接告诉发起方。承接范围可以写得比请求窄，写明不接受的部分和理由；整个都接不了的，请书记员回滚到“提出”并写原因。下发关系不做接单确认：承接的 +0 先交方案，方案里有“对需求的理解”一节，发出方确认方案就是开工。

交付包写好自己上传（`docs.py upload <草稿路径> --apply`），再请书记员填“交付包”字段、确认“执行”这一步。发出方验收不通过时，请书记员把需求回滚到“执行”并写原因；交付包字段会被清空，改好后重新交。答复没建工作项的任务（执行关系的封闭任务，编号像 `2101-3`）时，“关联工作项”写它的编号，上传完就算交了，不找书记员；派活的会话用 `docs.py accept` 验收，不通过的照它写的原因改好再交。

## 栏目随关系变化

适用的栏目一个不删，没有内容写“无”；下表标“不写”的栏目整节删掉；不临时加栏目。表里没列的栏目，三种关系都写。

| 栏目 | 执行 | 下发 | 跨序列 |
| --- | --- | --- | --- |
| 结论与机制 | 不写 | 写 | 不写 |
| 判断的变化 | 不写，封闭任务不评价研究方向 | 写 | 写 |
| 决定与待决事项 | 不写 | 写 | 不写 |
| 和方案的出入 | 不写 | 写 | 不写 |
| 子任务汇总 | 不写 | 写 | 不写 |
| 偏差和使用限制 | 不写 | 不写 | 写 |
| 异常和发现 | 写 | 不写，写进判断的变化或待决事项 | 不写，写进判断的变化 |
| 对本序列标准的反馈 | 不写 | 写 | 不写 |
| 状态包 | 只写当前状态和风险 | 四项都写 | 不写，由发起方在跨序列需求的主文档里维护 |

## 填写规则

- 包头“版本”写第几版和日期，第一次交是“第 1 版（YYYY-MM-DD）”；验收不通过、改好后重新交的，版本号比上一次交的大 1。重新交时改原来那份草稿或者另写一份都行，再跑一次 `docs.py upload`：它新建一份文档挂在需求的主文档下，上一版的文档留在原处；版本号没有加 1 的，脚本停下并写明该写第几版。传好以后请书记员再跑一次 `workitem.py reply`，把“交付包”字段换成新链接。
- 认知层先给结论。接收方要据此决定下一步，要点放在开头。
- 逐条对照只对照需求包里的验收标准。执行关系不评价研究方向，那是下发的需求和 +1 的事。
- 结论里的分数写明出处：正式分引用质量序列交付的打分记录，自己跑的照实写是开发分。原始数据放进事实依据，正文不罗列。
- 下发关系的交付包和执行关系最大的区别在“判断的变化”：承接的 +0 要说明自己对问题的理解变了什么、为什么变。
- 待决事项写成选项，接收方可以直接选。需要别的序列配合的事也写在这里，由 +1 决定是否发跨序列的需求包。
- 跨序列关系交付时只交需求包要的东西，额外的发现写进“判断的变化”。
- 做不到时写清缺什么、建议怎么办。写清楚的“做不到”算合格的交付。
- 发现规格能被绕过、数据有问题这类情况，写进“异常和发现”或“判断的变化”，附复现步骤，不自己动手修。

## 各序列的填写要点

### 执行

| 序列 | 逐条对照的主要内容 | 异常和发现的例子 |
| --- | --- | --- |
| 产品 | 访谈记录、现状工作流、失败案例和现成数据，每份标来源 | 调研对象的说法和实验日志对不上 |
| 算法 | 每个变体的结果和运行 ID，包括失败的；基线复现 | 规格能被绕过，比如计时没有覆盖数据加载 |
| 工程 | 代码位置、测试记录、已知限制 | 现有组件的接口和规格不一致 |
| 基础设施 | 环境配置、预检脚本、越权测试结果 | 发现越权尝试 |
| 质量 | 打分结果、错误分析、对评测本身的红队记录 | 评测集本身有问题 |
| 项目管理 | 写入结果和异常清单 | 台账和文档对不上 |
| 外联 | 材料草稿、每条内容在台账里的出处 | 草稿里的数字和台账里的正式分不一致 |

### 下发

| 序列 | 结论与机制 | 判断的变化的例子 | 常见的待决事项 |
| --- | --- | --- | --- |
| 产品 | 需求文档草案、现状基线及其证据、试点结论 | 原以为工程师最在意速度，访谈后发现更在意改动能不能看懂 | 判据要不要改；试点要不要扩大 |
| 算法 | 证伪结论、机制解释、适用边界 | 原以为优化效果来自搜索策略，消融后认为主要来自多次评测取平均 | 规格要不要修订；要不要上全量 |
| 工程 | 实验流程、运行记录样例、可复现情况 | 原以为缓存能省下大部分重复评测，正式评测必须真跑后，节省有限 | 要不要沉淀成共享组件；技术债什么时候还 |
| 基础设施 | 资源用量、工具失败分类、修订的工具封装 | 原以为工具失败主要来自限流，统计后发现多数是参数格式错误 | 要不要追加配额；权限策略要不要调整 |
| 质量 | Eval Set 和打分脚本的审计结果、正式分和打分记录 | 原以为提升来自方法，红队检查发现一部分来自数据泄漏 | 评测协议要不要修订 |
| 项目管理 | 关键路径、阻塞统计、交接失败案例 | 原以为阻塞多在等资源，统计后发现多在等人决定 | 决策队列要不要提高频次 |
| 外联 | 材料草稿、每个结论对应的工作项、对导师承诺的进展 | 原以为读者关心进度，追问显示更关心和人工基线的对比 | 材料模板要不要调整 |

### 跨序列

| 承接序列 | 接单时要确认的 | 交付时的交付物 |
| --- | --- | --- |
| 算法（承接产品） | 需求文档里的约束怎样落进规格 | 签字后的规格，逐条对应需求文档的判据 |
| 工程（承接算法） | 实现范围、和规格的对应关系 | 可重放的实验流程、运行记录样例；实现和规格的偏差 |
| 基础设施（承接算法、工程） | 哪些约束能由运行环境强制执行，哪些不能 | 已就绪的资源和环境；约束有效性的测试结果 |
| 质量（承接产品、算法、工程） | 要建或要用的 Eval Set、评测协议、要出的正式分 | Eval Set 的版本和评测协议；阈值核对的结果；正式分和每次打分的运行 ID |
| 算法等序列（承接质量） | 修订范围、对已有结果的影响 | 新版规格；受影响结果的处理办法 |
| 项目管理（承接各序列） | 字段、模板、台账查询的改动范围，是否要走组织规则变更 | 生效的字段、模板或查询，以及生效时间 |
| 外联（承接项目管理） | 材料的目的、读者和关注点 | 写好的材料，发出前由研究员签字 |
| 产品（较少承接） | 按通用栏目填写 | 按通用栏目填写 |
