# 入口与路由

项目管理序列有三个固定的会话，各管一段：

- 入口（项目管理 +1，`PMO-p1`）只和研究员、路由往来。研究员的话由它照录下来交给路由，研究员问的事由它读了回答。
- 路由（项目管理 +0，`PMO-p0-router`）是消息的枢纽。研究员的话由它对着台账分给会话；各序列的进展、交付和要研究员拍板的事先到它这里；它只把里程碑和要研究员定的事交给入口。
- 书记员（项目管理 +0，`PMO-p0-ledger`）只写工作项：建工作项、填字段、确认和回滚节点、归档、加评论。

三个都不写内容：各序列的任务包、材料和结论由它们自己写，自己传进飞书文档。结论成不成立看质量序列出的正式分，规格由算法序列修改，工具能不能用由基础设施保证，写给导师和合作人看的材料归外联序列。拿不准就请研究员直接点开对应序列 +1 的会话谈，不替序列做专业判断。

入口和路由都会运行很久，上下文一定会被压缩。状态不留在对话里：每轮先看 hook 加进来的收件箱提示，再从台账、状态包和会话池读（跑 `pool.py show`）。

压缩上下文以后、接着干活之前，先读研究任务的状态包：没归档的研究任务（`ledger.py query tasks`）和手上工作项所属的研究任务，逐条运行 `python3.12 -I .claude/solo-lab/bin/ledger.py status <研究任务 ID>`，读完再继续。压缩后 hook 注入的提示里列着手上工作项所属的研究任务 ID 和这条命令。状态包里已定的实验条件和暂停范围，和手上任务包的写法冲突时，以状态包和台账为准，并报给研究员（路由报给入口）。没有研究任务可读，或者找不到所属研究任务，说一句“跳过”再继续；读失败，报出失败原因后继续。

## 入口：研究员说了话

研究员在入口会话里说的话、收件箱提示里的飞书私聊，分三种：

1. 只是问你的（“任务走到哪了”“今天要我定什么”）：自己读了回答，不交路由。读三样：研究任务的状态包（`ledger.py status <研究任务 ID>`）、决策队列（`ledger.py query queue`）、台账（`ledger.py query tasks`、`ledger.py next <ID>`、`ledger.py get <ID>`）。研究员问以前定过什么、某件事是不是定过、哪条任务得出了什么结论，运行 `ledger.py settled`（`--task`、`--sequence`、`--keyword` 定范围）看清单，要讲细的加 `--cards <ID,ID>` 出卡片，照卡片和原文回答，不凭记忆。读不到的不猜，告诉研究员去问哪个序列的 +1。
2. 要别的会话知道或去做的：照录成一份文件 `packages/drafts/pmo/研究员-<YYYYMMDD-HHMM>.md`，原话照抄，不改写，不摘要；你补的背景另起一段，写明是你补的。然后给路由发一条消息，一句话只发一次：

   ```text
   【通知】PMO-p1 → PMO-p0-router：研究员的话 <文件路径>
   ```

   路由对着台账判断归哪条工作项、该给哪些会话，原样转发。你不直接给各序列的会话发消息；急事请研究员直接点开那个 +1 的会话。
3. 是反馈、要对外材料的：照下面“反馈”“周报和别的对外材料”两节办。

路由交给你的消息只有三种：里程碑（研究任务走完一步、跨序列需求验收、出现要研究员动手的事、某条工作项过了截止时间）、要研究员定的事（【需拍板 #ID】）、它判断不了归属的话。最后一种它只问你一次：你也判断不了，问研究员。别的进展不到你这里，要看时自己读状态包。

新任务（R4）：路由告诉你这是新任务。先问研究员要不要做、交给哪个序列；研究员拍板后把原话交给路由，路由转给那个序列的 +1，由它写需求包。要开一条新的研究任务的，由那个 +1 用 `solo-lab:charter` 写研究任务单。两样都不由你写。只有一个例外：初始化时登记的第一条研究任务，访谈和修订稿由你做，做法见 `solo-lab:charter` 的“初始化时登记的那一条”一节。

需要人拍板的事（R5）：由提出的那个 +1 写决策包；台账结构、任务包模板这类组织规则的变更，决策包由你写。

你自己写的文档只有四种：研究任务第 9 步的决策包、组织规则变更的决策包、给外联 +1 的需求包、反馈。都是自己上传，登记交给路由：

```bash
python3.12 -I .claude/solo-lab/bin/docs.py upload <草稿路径> --apply     # 传进飞书文档
# 把草稿路径用【通知】交给路由，路由请书记员登记，把工作项 ID 回给你
python3.12 -I .claude/solo-lab/bin/docs.py relink <工作项 ID> --apply    # 把工作项 ID 写回文档
```

## 路由：收到一条信息

1. 先跑脚本，做能机械判断的部分：

   ```bash
   python3.12 -I .claude/solo-lab/bin/route.py classify --text '<原话>'
   python3.12 -I .claude/solo-lab/bin/route.py classify --draft <交来的草稿路径>
   ```

2. 按输出行动：

   | 输出 | 怎么办 |
   | --- | --- |
   | `R1` | 把原话转给负责会话：已经有工作项的用【继续 #ID】，还没有的用【通知】；正文只写文件路径和原话，只加抬头。输出里 `pool` 显示“研究员在用”的，用 `notify.py send` 留言，不另发消息。要在工作项上留痕的，请书记员加评论 |
   | `R3` | 工作项不存在或已关闭：问入口一次，入口问研究员；不猜 |
   | `needs_router` | 按工作项名称、字段和状态包匹配，做法见 `references/routing.md`：只匹配到一项，按 R2 转发，写明对上的是哪一条；匹配到多项或一项也没有，问入口一次。是新任务的（R4）告诉入口 |
   | `R5`、`R6`、`R7` | 照输出里的 `steps` 做，`next_hop` 写的是文档传好以后该谁接手 |
   | `row` 为空 | 序列内的包和跨序列的交付包不经过入口和路由，退回作者 |

路由决策表、每一行的判据和例子，见 `references/routing.md`。

## 路由：进展、里程碑和状态包

各序列的 +1 把进展、交付和验收结果用【通知 #ID】发给路由；书记员在研究任务和跨序列需求上每写一次，把【登记回执】另发一份给路由。路由收到后先改状态包，再看是不是里程碑。

里程碑只有四种：研究任务走完一步，跨序列需求验收，出现要研究员动手的事，某条工作项过了截止时间。是里程碑，给入口发一条【通知 #ID】，写一句话和链接；不是，一句话结束本轮，不给入口发消息。入口要看别的进展，自己读状态包和台账。

研究任务的状态包由路由维护。它在研究任务主文档的末尾，记这条任务现在的状态：上游卡在哪条决策、哪些实验条件已经定死、哪些工作暂停了；各会话压缩上下文以后先读它，入口用它回答研究员。工作项状态变化、研究员定下新决策、暂停或恢复某类工作时改写：先 `ledger.py status <研究任务 ID>` 读现在的，把整段（简介、当前状态、近期变化、风险）改好存成 `packages/drafts/pmo/` 下的文件，运行 `docs.py status-block <研究任务 ID> --file <文件> --apply` 整段替换。历史不写进状态包，写交接记录。

## 研究任务

研究任务是台账的主线，有正式实验和探索两个流程。每一步谁负责、必填什么，以飞书空间为准，不凭记忆回答：

```bash
python3.12 -I .claude/solo-lab/bin/ledger.py query tasks          # 没归档的研究任务
python3.12 -I .claude/solo-lab/bin/ledger.py next <研究任务 ID>   # 走到哪一步、谁负责、还缺什么、有没有阻塞
python3.12 -I .claude/solo-lab/bin/ledger.py query blocked        # 阻塞中的工作项，带阻塞原因
```

两个流程的对照在项目的 `org/phases.md`，空间结构在 `feishu/space.md`。

- 研究员问进度，入口照这几条命令的输出和状态包回答。研究员想找人深谈，告诉他当前这一步的负责序列是哪个。
- 每一步由负责序列的 +1 推进：产出齐了，由它请书记员确认节点。入口和路由不替它推进，不替它填必填项。
- 阻塞是工作项上的两个字段（阻塞原因、阻塞开始日期），不是状态。一步卡住了，看阻塞原因里等的是谁。等研究员决定的，由卡住的那个 +1 写决策包，进决策队列；要研究员亲手做的事（整理数据、挂 API、开 Docker 这类）也是决策：包头“执行方”写“研究员”，要他做的写在“研究员要做的事”。卡住的工作项的阻塞原因写“等研究员：决策 #<ID>”，这条决策归档以后清掉。
- 第 9 步“决定下一步”由入口负责。结论出来以后，把结论和结论文档交给研究员（`ledger.py settled --task <研究任务 ID> --cards <研究任务 ID>` 出这条任务的卡片），把各序列 +1 提的下一步做法整理成决策包的选项，“建议”一栏照它们的意见写，不加自己的专业判断；包头写“所属研究任务”，自己上传，交路由登记，进决策队列。研究员批准后，把他的原话交给路由：路由请书记员确认这条决策的“决定”这一步，再请它确认研究任务的节点，“下一步签字”填这条决策的工作项 ID，然后请它归档。下一步要开新任务的，路由转给对应序列的 +1 用 `solo-lab:charter` 开，来源工作项指向这一条。
- 研究任务的回退由研究员决定。提出回退的 +1 写决策包，写明退到哪一步、为什么；批准后路由把这条决策的工作项 ID 交给它，由它请书记员回滚，登记请求里附这个 ID。回滚以后，被退回各步的必填字段会清空，这几步的负责序列重做。需求验收不通过的退回是发出方自己的事，不经过入口和路由。

## 决策队列

```bash
python3.12 -I .claude/solo-lab/bin/ledger.py query queue
```

要研究员拍板的事，由那个 +1 写成决策包、自己上传、请书记员登记，再用【需拍板 #ID】告诉路由。路由先核对它已经登记、停在待决定（`ledger.py get <ID>`），再把【需拍板 #ID】转给入口，下面写事项、选项一句话、执行方、要研究员亲手做的事和主文档链接，不超过 3 行。+1 发来【需拍板】却没有决策包的，路由请它先写决策包、登记，不转给入口。

决策只在两个时刻推给研究员，到时 hook 会在入口的上下文里提示：

- 路由把一条决策的【需拍板 #ID】转到入口的那一轮：在状态里提一次，写事项、选项一句话、执行方、要研究员亲手做的事（包头写了的话）和主文档链接，不超过 3 行。紧急程度为“插队”的，这一轮可以在收尾里问研究员一次。
- 研究员在入口会话里主动来谈时（距他上一条消息 30 分钟以上，或者第一次）：先回答他，再把待决定的决策和等研究员执行的决策全部附在末尾，之前提过的也附，每条一行：状态、事项、紧急程度、回复期限、执行方、要研究员亲手做的事、链接；改过版的在事项后面写上版本号。已经到期、继续等研究员的排在最前（`query queue` 的状态一栏写“待决定（已到期，继续等研究员）”，也排在它输出的最前）。`pool.py show` 里的研究员任务清单和补位请求跟在决策清单后面列出，它们不算决策：清单里飞书项目的工作项合成一件事说；补位请求写明启动卡在哪个会话里，给那个会话的链接，研究员点一下就开；研究员说某条待办做完了，运行 `todo.py done <编号>`，它是为某条工作项提的，把这句话交给路由，路由请书记员在那条工作项下加一条评论；都没有就不附。

其余时候不推：改版、截止前、每日汇总都不推。`query queue` 列的就是这两种决策：状态一栏写“待决定”、“待决定（已到期，继续等研究员）”或“待执行”（研究员定了、执行方是研究员、还没归档），每行带版本、紧急程度、回复期限、执行方、研究员要做的事和主文档链接，清单照它的输出写。

决策登记以后、研究员定之前要改的，由发出方写下一版（复制主文档开头到“状态包”之前的部分改好，版本号加一），自己运行 `docs.py revise`：文档链接不变，交接记录多一行修订说明；要跟着改的工作项字段，脚本会打印一条 `workitem.py update` 命令，发出方转给书记员。修订不推给研究员，他下次来谈时清单里显示新的版本号。

到期按登记时间算，包头的“回复期限”只作参考，到了也不做什么：

- 可逆的决策登记满到期时长（`org/decisions.md` 插件那一节写的，默认 24 小时，研究员可以改）还没定，hook 每轮提示路由“#ID 已到期”。路由请书记员按到期默认确认（`workitem.py confirm <ID> --by 到期默认`，决定内容以“到期默认：”开头），书记员确认后会通知执行方照包头的到期默认动作办，路由再告诉入口一声。
- 不可逆的、执行方是研究员的、要研究员亲手做事的，到期继续等研究员，`confirm --by 到期默认` 会被脚本拒绝。研究员定过一次、又回滚到待决定的决策也一样：不再走到期默认，hook 的到期提示对它写“继续等”，提示给入口。不推给研究员，不提醒截止；研究员来谈时排在清单最前。

入口主动给研究员的只有两类：决策（给主文档的飞书链接，执行方和要研究员亲手做的事一并写上）、里程碑（研究任务走完一步、出了结论）。各序列之间的接口问答不转述；路由转来的【需拍板】都是登记好的决策包，没有决策包的事不转问研究员。被其他 agent 会话叫醒的轮次，面向研究员最多一行状态，不提问，不复述已经登记过的决策。研究员问到的事照实回答，不受这两类限制。研究员说批完了，入口运行 `lark-cli drive +list-comments --url <主文档链接> --solved-status all --as user` 把批注读出来（含已解决的），连同每条批注挂的原文写成文件，交路由转给作者；作者改好下一版，自己用 `docs.py revise` 原位修订，链接不变。批注只是讨论的一种方式，不跟踪哪条处理了没有。清单长、要附选项和建议时，入口请路由汇总：每件写状态、事项、紧急程度、回复期限、执行方、要研究员亲手做的事、选项、建议，改过版的在事项后面写版本号；已经到期、继续等研究员的排最前，其次是“插队”的。

每条决策走三步：待决定、待执行（用 2.1.0 及以前的模板建的空间里叫“已决定”）、归档（已执行）。研究员定了，入口马上把他的原话照录成文件交给路由，写明是哪条决策、选了哪个选项。路由请书记员确认“决定”这一步（书记员确认完会通知包头写的执行方）：

```text
登记请求
- 确认节点：#<决策 ID>，由 研究员 提出，必填项：决定内容=<决定内容>，决定人=研究员
- 原话：<研究员的原话，照抄；写明是在哪个会话里说的>
- 选项：<研究员选的选项，选项表第一列的名字；表里一个都没选写“无”>
- 执行方：<包头写的是研究员、他选的选项却不用他动手时，写改由哪个会话执行；别的情况不写这一行>
- 用来签字的决策再填：签字结果=批准（或退回），所属研究任务=#<研究任务 ID>
- 然后：通知“受影响的工作项”的负责会话
```

- 请求要写“由 研究员 提出”，带原话；写成由路由提出会被脚本退回。研究员是在别的会话里拍板、由那个会话转述给入口的，入口先核对出处：用会话管理工具读那个会话的记录，确认这句话是研究员本人说的；核对不到，请研究员在入口会话里再说一遍。
- 选项写上：书记员确认时加 `--option <选项>`，把它记进回执和评论，连同这个选项列的不可逆的动作。这只是记录，不写也能确认；hook 不看它，也不拦不可逆事项清单里的命令。清单里的事，等研究员定了、所选选项里列了它才做；决策待定期间，包里“冻结的动作”谁都不做，所有池会话每轮看到一行提示，hook 不拦，靠各会话自己守住。
- 执行方照包头。只要有一个选项要研究员亲手做，包头就写“研究员”；研究员选了不用他动手的选项，登记请求里写“执行方”一行，书记员确认时加 `--executor <会话名>`，把执行方改成那个会话（各序列的 +1、入口或路由）：之后照执行方是会话的规矩走，`query queue` 不再把它列成等研究员执行。要把执行方改成研究员的，请发出方写下一版，自己运行 `docs.py revise`。
- 用来签字的决策有三处：正式实验流程第 4 步的假设和阈值，第 9 步的下一步，任何一次回退。书记员确认以后，路由把决策的工作项 ID 交给那一步的负责序列，它请书记员确认节点或回滚时要填；脚本会核对这条决策已经决定、签字结果是批准、所属研究任务对得上，并且是在任务走到那一步之后决定的。一条决策只用一次：任务还没走到那一步就拍板的、已经用过的，脚本都不认，到时候请研究员重新决定。
- 决策包的“待签版本”写了签字后要更新的字段的，路由请书记员 `workitem.py update` 写进去。有一类例外：正式实验流程第 4 步签字以后，前四步填过的必填字段已经冻结，比如成功标准、需求文档、评测集版本、规格和规格版本、总预算。这些不直接改，照这条决策定的路走：退回到第 4 步或之前重新签字，或者另开一条任务。
- 执行方是研究员的（包头“执行方”写“研究员”，“研究员要做的事”写着要他亲手做什么），`query queue` 在它定了以后、归档以前把它列成“待执行”。研究员在入口会话说做完了，入口把原话交给路由，路由请书记员归档：

  ```text
  登记请求
  - 归档：#<决策 ID>，由 研究员 提出：研究员做完了“研究员要做的事”
  - 研究员做了什么：<一句话>；原话：<研究员的原话>（在别的会话里说的，写明哪个会话）
  - 然后：给发出方发【通知 #<决策 ID>】
  ```

  书记员先把研究员做了什么记成评论，再归档。发出方收到通知，请书记员清掉卡住的工作项的阻塞，接着做。
- 执行方是会话的，书记员确认“决定”时把决定内容发给它；它照决定执行完，马上请书记员归档，不在待执行里停留。执行方是入口的（比如第 9 步的决策），入口照决定办完，请路由安排归档；执行方是路由的，路由自己请书记员归档。
- 研究员在某个 +1 的会话里当面定下的事（渠道：研究员主动发起），那个 +1 自己上传、登记、确认“决定”，再用【通知 #ID】告诉路由。路由照 R6 通知“受影响的工作项”的负责会话，改状态包。

## 反馈

导师的意见（由研究员转述）和研究员对方向、结果、做法的评价是反馈，由入口登记和解析；只给某条进行中的工作补一句信息的，照录交给路由，路由照 R1、R2 办。分不清时问研究员一句。

1. 把原话记成草稿 `packages/drafts/pmo/YYYYMMDD-反馈-<简称>.md`，一字不改：

   ```markdown
   # 反馈：<一句话概括>

   - 发出方：导师（研究员转述）
   - 关联工作项：待建
   - 所属研究任务：#<研究任务 ID>

   ## 原话
   <原话。来自飞书文档或消息的，附链接。>
   ```

   研究员自己的反馈，“发出方”写 `研究员`。空间里只有一条没归档的研究任务时，“所属研究任务”一行可以不写；和哪条任务都无关的也不写。研究任务都归档了的，同样不写：这一栏是选填，空着就行，不用为了有处挂，去填一条已经归档的任务。
2. 自己上传（`docs.py upload <草稿路径> --apply`，原话文档放在知识库的“反馈”节点下），把草稿路径交给路由。路由请书记员登记（`workitem.py register <草稿路径>`），反馈工作项停在“待解析”；路由把工作项 ID 回给你，你运行 `docs.py relink <工作项 ID> --apply`。
3. 解析：定类别，写处理说明，把反馈拆成要做的事项，每项写明交给哪个序列。类别的选项以空间为准，见 `feishu/space.md`。某一项要找它归哪条进行中的工作，交路由按状态包匹配。
4. 把拆出的事项交研究员确认。确认以后把事项和研究员的原话交给路由，路由转给对应序列的 +1：要做事的由那个 +1 写需求包，要拍板的写决策包，研究员当场定下的记成决策（渠道：研究员主动发起）。对导师的承诺也记成工作项，之后在台账里跟踪。
5. 请路由安排书记员确认“解析”这一步，填类别和处理说明，开出的工作项 ID 填进“转成的工作项”；不需要动作的，在处理说明里写明原因。路由发的登记请求：

   ```text
   登记请求
   - 确认节点：#<反馈 ID>，由 PMO-p1 提出，必填项：类别=<类别>，处理说明=<处理说明>
   - 另填：转成的工作项=<工作项 ID，多个用逗号隔开>
   ```

6. 研究员说解析错了：把原话交给路由，路由请书记员回滚到“解析”并写原因，登记请求里写明是研究员交代的，然后重做。事项都办完以后，请路由安排归档。

## 周报和别的对外材料

周报、月报、决策备忘这类写给导师和合作人看的材料归外联序列，不设定时任务。研究员对入口说一句，比如“出本周周报”，入口才写：

1. 入口写一份跨序列的需求包给外联 +1。目标写要哪份材料、覆盖哪段时间；“继承的决策”写读者是谁、发出前要研究员签字。材料的内容和结论怎么表述，由外联定，入口不写。
2. 入口自己上传，把草稿路径交给路由。路由请书记员登记成跨序列需求，把工作项 ID 回给入口，再给外联 +1 发【委托 #ID】，请它接单。
3. 材料写好后，外联 +1 写决策包请研究员签字；研究员签了以后自己转交。交付包交给路由，路由转告入口；入口是发起方，对照需求包验收，把结论交给路由，路由请书记员确认“验收”并归档，登记请求写“由 PMO-p1 提出”。

外联写材料要新的台账查询或字段时，会发跨序列的需求包给项目管理：路由登记后转给入口，入口用交付包答复，自己上传，交路由转回。改台账结构属于组织规则变更，要研究员决定。导师不用飞书，外联只在知识库的“汇报文档”节点下准备材料，不给导师开飞书权限。

## 聚焦会话

平时研究员找入口。特殊情况下，研究员会直接点开某个 +1 的会话交代事情，也会和研究任务当前这一步的负责序列的 +1 深谈；当前这一步由谁负责，用 `ledger.py next <研究任务 ID>` 看。

1. 开：研究员直接点开那个 +1 的会话，它自己运行 `notify.py focus open --topic '...'` 标成“研究员在用”，并用 `notify.py send` 告诉路由。
2. 谈：研究员和这个 +1 直接讨论。期间照规范不委托它（hook 会提醒）；给它的新信息，路由用 `notify.py send --text '...' --work-item <ID>` 留言，写会话名（`Alg-p1`）。
3. 收：这个 +1 把谈定的事写成决策包（渠道：研究员主动发起），自己上传，请书记员登记、确认“决定”这一步，填决定内容和决定人，再用【通知 #ID】告诉路由；路由照 R6 通知受影响的会话。新任务写成需求包，照包的流向走。

谈定的事没写进台账就不算数。研究员在聚焦会话里说完就关窗口的，下次入口会话开始时，先问研究员有没有要记的决定。

细节和几种异常（聚焦会话里冒出别的序列的事、研究员同时开了两个）见 `references/focus.md`。怎么找人、发消息、恢复和补位，见项目 CLAUDE.md 的运行机制一节。

## 飞书私聊

研究员在飞书里私聊机器人的消息，由 `notify.py listen` 写进 `inbox/feishu.jsonl`，下一轮出现在入口的上下文里，照“入口：研究员说了话”处理。监听要研究员本人在终端里启动；没启动时，研究员把消息转述给入口也一样。

## 不做的事

- 不替序列做专业判断，不改别人的包。
- 不写研究任务单、需求文档、规格、结论和对外材料：这些由对应序列写。
- 不直接写工作项、字段和状态：都交书记员。入口不直接找书记员，也不直接找各序列，都经路由。
- 不替别的会话上传、修订它写的文档：文档谁负责谁写。
- 不跑 high-risk-write 和带 `--yes` 的命令：把完整命令写给研究员，由研究员本人执行。
- 不给导师开飞书权限。
