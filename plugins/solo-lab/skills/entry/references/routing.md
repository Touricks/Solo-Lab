# 路由决策表

逐条往下判，命中就停；判断不了就上交，不猜。路由的质量更多取决于输入是否规范：包名带作者的会话名、工作项有来源字段，这两条约束比路由提示词写得多巧更重要。

| 行 | 收到什么 | 判据 | 动作 | 谁来判 |
| --- | --- | --- | --- | --- |
| R1 | 带工作项 ID 或会话名的信息 | ID 存在，工作项未关闭 | 在该工作项下加带会话标签的评论，交给负责会话接着做；该序列的 +2 正被研究员直接用着的，留言给它 | 脚本 |
| R2 | 没带 ID 的补充信息 | 按工作项名称、字段和状态包只匹配到一项进行中的工作 | 同 R1，并在评论里写明匹配依据 | 路由 +1 |
| R3 | 没带 ID 的补充信息 | 匹配到多项，或一项也没有 | 交项目管理 +2 判断 | 脚本或路由 |
| R4 | 新任务 | 无 | 交项目管理 +2；研究员拍板后，由对应序列的 +2 发需求包 | 入口 |
| R5 | 需要人拍板的事 | 无 | 建决策工作项，停在“待决定”，进决策队列 | 入口；交来的决策包由脚本识别 |
| R6 | 研究员当面定下的事 | 决策包的渠道是“研究员主动发起”，决定内容和决定人写全了 | 建决策工作项，填决定内容和决定人，确认“决定”这一步，通知受影响工作项的负责会话 | 脚本 |
| R7 | 各序列交来的包 | 按包类型和关系 | 跨序列的需求包转给路由查重、登记；别的照包的流向 | 脚本 |

## 脚本怎么判

`route.py classify --text`：

- 找工作项 ID（`#` 后面的数字，或九到十二位的长数字）和会话名（如 `Alg-p1-02`、`Alg-p0-2003`；+0 的会话名里带工作项 ID）。
- 有 ID 的，读台账：存在且未关闭，命中 R1，输出负责会话，和这个序列是否开着聚焦会话；不存在或已关闭，输出 R3。已验收、归档、已终止的工作项算已关闭。
- 只有会话名的，命中 R1，输出这个会话的角色。
- 都没有的，输出 `needs_router`，候选是 R2 到 R5。脚本不按关键词猜“新任务”或“要拍板”，这些交给模型判断。

`route.py classify --draft`：先跑包检查，通不过就退回作者；然后按包类型和关系判 R5、R6、R7，输出下一跳和步骤。

会话名大小写都认（`alg-p1-02` 就是 `Alg-p1-02`）。+0 的会话名分两种：后面是三位以上数字的（`Alg-p0-2003`）带着工作项 ID，脚本按工作项判；会话池里的池位名是两位序号（`Alg-p0-01`），只当会话名。R1 的输出还带 `pool`：负责会话的桌面会话 ID、忙闲，以及研究员是不是正在用它。

## 交来的包怎么转

| 交来的包 | 行 | 下一跳 | 步骤 |
| --- | --- | --- | --- |
| 跨序列的需求包 | R7 | 路由 | 发起方 +2 本该直接交给路由；交到入口的，转给路由。路由对照台账查重复和冲突，请书记员登记（“提出”这一步随登记确认，工作项停在“待接单”），把工作项 ID 回给发起方，由它直接委托承接方 +2 |
| 跨序列的交付包 | 无 | 无 | 不经过入口和路由：承接方请书记员把交付包挂到跨序列需求下、确认“执行”这一步，工作项到“待验收”，再直接交付给发起方 +2 |
| 决策包，渠道是决策队列 | R5 | 书记员 | 登记后停在“待决定”；登记回执到的那一轮在状态里提一次，写上执行方和要研究员亲手做的事（“插队”的可以在收尾里问研究员一次），研究员主动来谈时连同其余等研究员的决策列出。研究员定了就确认“决定”，到“待执行”，书记员通知执行方；执行方是研究员的，研究员说做完了才归档；执行方是会话的，它照决定执行完马上请书记员归档 |
| 决策包，渠道是研究员主动发起 | R6 | 书记员 | 登记后接着确认“决定”这一步，填决定内容和决定人，书记员通知执行方；通知受影响的会话 |
| 下发、执行关系的包 | 无 | 无 | 序列内的包不经过入口，退回作者 |

跨序列需求接下来怎么走：

- 接单：承接方 +2 自己给书记员发登记请求（确认节点：#<ID>，由 <承接方 +2 的会话名> 提出），写上需求复述、承接范围和预计交付时间，书记员确认“接单”这一步时填进去，工作项到“执行中”；承接方再把这三项直接告诉发起方。交付包也由承接方自己请书记员登记。承接范围可以写得比请求窄。
- 不接：承接方请书记员回滚到“提出”并写原因，工作项回到发出方手里，状态是“已退回”。发出方改完需求包，再请书记员确认“提出”，就是新一轮。
- 验收：发起方 +2 验收通过，请书记员确认“验收”这一步；不通过，请书记员回滚到“执行”并写原因，交付包字段会清空，承接方改好后重新交。
- 请质量序列出正式分、请外联序列出材料，走的都是这条路。
- 这些往来都在两个 +2 之间，入口不转手。书记员在跨序列需求上每写一次，回执另发一份给路由；路由维护 `packages/drafts/pmo/跨序列协调记录.md`，往来里出现改范围、改标准、改冻结项的内容，两边说法对不上，或者过了期限没有动静，才报给入口。入口要看进展，跑 `python3.12 -I .claude/solo-lab/bin/route.py cross`（不带参数列出最近有往来的各条，带工作项 ID 列出这一条的全部往来）。

## 会话池里的两句话

这两句不进路由决策表，入口直接照办：

- 研究员说“补位”或“再开一个 …”：这一轮可以开会话。会话一层开一层，新会话在侧栏里嵌在开它的会话下面：路由由入口开，书记员由路由开；其余序列的 +1 由那个序列的 +2 开，+0 由它上面的 +1 开。研究员要在开它的那个会话里说；开好马上 `route.py expect` 预登记。研究员没这么说时记补位请求（`route.py refill`），开这个角色的会话提一张启动卡，研究员点一下才开；研究员来谈时，入口把它跟在决策清单后面列出，补位请求不算决策。
- 研究员说“恢复”（重启或睡眠以后）：入口运行 `route.py pool --recover`，照清单发【继续 #ID】；书记员先用 `ledger.py register <草稿> --resume` 补完写到一半的登记。
- 研究员在网页上终止了一批工作项以后（比如研究任务改了思路，下面的需求包不做了）：入口运行 `route.py pool --prune`，它对照台账列出认领表里已经归档或终止的工作项；核对清单后加 `--apply` 移出。台账读不到时它不写。归档的工作项书记员归档时已经移出，不用另跑。
- 补位请求不要了：`route.py refill <角色> --count 0` 撤回这个角色的补位请求，入口的清单里不再列它。
- 补位请求怎么办成：某个会话运行 `route.py refill <角色>` 以后，开这个角色的会话（+1 归 +2 开，+0 归它上面的 +1 开）在同一轮提一张启动卡。`route.py pool` 的“补位请求”一行写着启动卡在哪个会话里；向研究员列补位请求时给那个会话的链接，他点进去点一下卡片，会话就开出来。写着“还没有提启动卡”的，给开这个角色的会话发【通知】请它提。
- 研究员任务清单：`route.py pool` 里“研究员任务 N”各行，是会话请研究员动一下手、又没有选项要挑的事。研究员来谈时跟在决策清单后面列出，不算决策。他说做完了，运行 `route.py todo done <N> --note '<他的原话>'`；这一条是为某条工作项提的，照输出请书记员在那条工作项下加一条评论，再告诉提出它的会话。
- 清单里的“研究员任务·飞书项目”一行，是等研究员在网页上终止或删除的工作项（建错的、不做了的，书记员归档不了）。不管下面有几条，只当成一件事跟研究员说一次：“飞书项目里有 N 条工作项等你处理”，把每条的名称、原因和链接附上。平时不去查他处理了没有。他说处理完了，运行 `route.py pool --prune`，核对后加 `--apply`：它读一次台账，只划掉确实已经终止或删除的，同时把认领表里对应的条目移出；还没处理的留在清单上，把剩下哪几条告诉他。
- 研究员批注：交给研究员定的决策包和研究任务单，给的是主文档的飞书链接。他说批完了，运行 `lark-cli drive +list-comments --url <主文档链接> --solved-status all --as user`，把每条批注连同它挂的原文（返回里的 `quote`）转给作者。批注只是讨论的一种方式，不跟踪哪条处理了没有。

## 反馈和对外材料不进路由决策表

- 反馈：导师的意见和研究员对方向、结果、做法的评价。入口把原话请书记员登记成反馈工作项，自己解析，拆出的事项经研究员确认后交对应序列的 +2。做法见 `../SKILL.md` 的“反馈”一节。
- 要对外材料：研究员说“出本周周报”这类话，入口给外联 +2 发跨序列的需求包。不设定时任务，研究员说了才发。

## 路由 +1 怎么按状态包匹配

1. `ledger.py query open`（必要时加 `--sequence`，或查 `cross`、`tasks`）列出进行中的工作项和它们的名称。
2. 对候选逐个 `ledger.py get <ID>` 看字段（发出方、负责会话、来源工作项、所属研究任务等），`ledger.py status <ID>` 读主文档的状态包。
3. 原话里提到的会话、角色、工作项、决策、文档、数据集、版本或节点，和某一项的名称、字段或状态包对得上的，记为匹配。
4. 只匹配到一项：R2，依据写清对上的是哪一条。匹配到多项或一项也没有：R3 上交。不要因为“最像”就选一个。

## 例子

这些例子也是路由测试集的种子：每条写明应当命中哪一行。真实运行时，把研究员的原话和实际路由结果追加进 `org/routing-log.md`，误路由的单独标出，用来量路由准确率。

| 研究员的原话 | 应当命中 | 理由 |
| --- | --- | --- |
| “#2101 的访谈记录我补到文档里了” | R1 | 带工作项 ID，未关闭 |
| “Alg-p1-02 那边的消融跑完了吗” | R1 | 带会话名 |
| “规格 v2 里的种子数改成 5 个” | R2 或 R3 | 没带 ID；规格 v2 只出现在一项进行中的工作的名称、字段或状态包里才是 R2 |
| “再开一个方向：试试用 LLM 生成特征” | R4 | 新任务；研究员拍板后交对应序列的 +2，要开研究任务的由它写研究任务单 |
| “要不要追加 100 GPU 小时” | R5 | 超预算，研究员拍板 |
| 聚焦会话交来的“停止条件从搜索开始计时” | R6 | 渠道是研究员主动发起 |
| 算法 +2 交来的跨序列需求包 | R7 | 转给路由查重、登记，登记以后算法 +2 直接委托承接方 +2 |
| “导师说下周想看和人工基线的对比” | 不进表，按反馈办 | 导师的意见：登记成反馈工作项，由入口解析 |
| “出本周周报” | 不进表，发需求包 | 对外材料：入口给外联 +2 发跨序列的需求包 |
