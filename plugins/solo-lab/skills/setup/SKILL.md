# 初始化智能体组织

插件装一次，每个项目初始化一次。研究员做一件事：在项目目录开一个会话，说一句“用 solo-lab 初始化这个目录”。其余由这个会话做完。会话池大到要分两轮开时（默认的池一轮开完），它会停下来请研究员回一句“继续开池”。它叫初始化会话，做完以后留作研究员自己的会话，用来重新登录、检查和升级。

中途要研究员动手的有三种情况：命令行登录失效时扫一次码；项目文件写好以后信任一次这个目录；客户端弹出确认框时点一下。

| 步 | 做什么 | 写不写飞书 |
| --- | --- | --- |
| 1 | 把将要新建的清单发给研究员，开始计时，前置检查 | 不写 |
| 2 | 登录：只在有命令行登录失效时做 | 不写 |
| 3 | 写任务文件，生成项目文件；请研究员信任这个目录 | 不写 |
| 4 | 找项目空间，没有就用模板创建 | 新建项目空间 |
| 5 | 绑定项目空间，找到或新建知识空间 | 新建知识空间 |
| 6 | 开池（不写飞书）；开齐以后书记员建节点，上传并登记首条研究任务 | 新建节点、研究任务和主文档 |
| 7 | 写 `.env` | 不写 |
| 8 | 补读流程，四层检查 | 只读 |
| 9 | 结束计时，交接 | 不写 |

## 开始之前

### 插件目录和两类脚本

插件根目录是本技能目录往上两级。先把它解析成绝对路径，下面的命令里 `$PLUGIN` 指这个路径，`<项目目录>` 是项目目录的绝对路径。两个路径写进命令时都加双引号：路径里常有空格和方括号。

- 插件自带的脚本：`python3.12 -I "$PLUGIN/scripts/<脚本>" <子命令>`，脚本是 `setup.py`、`check.py`、`space.py` 和开池用的 `pool.py`。项目目录用 `--target` 给，在哪里运行都行。
- 项目里的副本：`python3.12 -I .claude/solo-lab/bin/<脚本>`。第 3 步生成以后才有，在项目目录里照这个写法原样运行，前面不加环境变量，后面不接管道。

### 支持的环境

只支持 Claude 桌面端。本会话要有开会话的工具 `start_session`，还要有给别的会话发消息的工具。

- 两样都没有，比如终端里的 `claude`：停下，告诉用户这一版只支持 Claude 桌面端，请他在桌面应用里选中项目目录新开一个会话，再说这句话。不换成别的做法。
- 工具都有，第 6 步开第一个会话却失败：走第 6 步的回退档。

### 项目目录

项目目录就是本会话所在的目录。

- 家目录和根目录不初始化，已经有另一运行平台的组织（`.agent-org/manifest.json`）的目录也不初始化。这两种情况 `init` 会报错停下。
- 用户另指目录的：用 `change_directory` 切过去，结束本轮，请用户回一句“继续”。工作目录到本轮结束才切换，后面的步骤要在项目目录里运行。

### 默认值

用户那句话里说了的照用，没说的取默认值，不停下来问。项目名是唯一的例外：没有就先问。

| 项 | 默认值 |
| --- | --- |
| 项目名（任务文件的 `name`） | 用户说的名字。说了项目名用项目名；没说项目名、说了飞书项目空间或知识空间的名字，用那个名字，两个都说了用项目空间的。都没说，或者只给了 simple_name、project_key 这类标识，先问研究员这个项目叫什么，不拿目录名代替：会话所在的目录名不一定规范，会话也可能没开在项目目录里。这个名字也是两个空间和侧栏分区的默认名 |
| 描述（`description`） | 用户的原话；没说写“待立项访谈补充”，交接时提醒 |
| 飞书项目空间（`feishu.meegle_space`） | 用户指定了已有的空间（名字、simple_name 或 project_key）就照写；没指定等于项目名。按名字精确查找：没有就用模板创建，有一个就沿用，两个以上停下列出 |
| 知识空间（`feishu.wiki_space`） | 等于项目名。翻完全部分页再判断：没有就新建，有一个就沿用，两个以上停下列出。要用的知识空间和别的同名、或者要换到一个同名的新空间时，在任务文件里加 `feishu.wiki_space_id`，写它的 space_id：写了就按它绑定，不按名字查 |
| 模板（`feishu.template_url`） | 不写，用约定文件 `orgspec/contract.json` 里的参考模板链接 |
| 会话池 | 12 个会话：七个序列各一个 +1，路由和书记员，工程、基础设施、质量各一个 +0。产品、算法、外联开池只开 +1（`pool.later` 默认是 `["liaison", "product", "alg"]`），有活时由它们的 +1 提补位 |
| 模型（`models`） | 入口（项目管理 +1）用 fable，其余会话都用 opus。会话的模型不能高于开它的会话：+1 高于本会话、+0 高于它的 +1 时，高出的不生效，沿用开它的会话的模型，开会话的工具也不报错。所以本会话选 fable，入口才能用 fable；本会话是 opus 时入口也是 opus，第 8 步的回读会把它报成模型不符，记进交接 |
| 上下文窗口 | 插件不设，跟账号和模型的默认值（现在是 100 万）。个别项目要设上限，由研究员在终端里往项目的 `.claude/settings.local.json` 写 `autoCompactWindow`：检查不把它报成漂移，重跑 `init --apply` 也不覆盖；这项设置只在会话进程启动时读，写完要退出并重开桌面应用 |
| 权限模式 | 全池和本会话一致：开会话时不填权限模式。本会话是 auto 模式时开池不用研究员点；是 bypass 模式时，应用每开一个会话都要研究员点一次，见第 6 步 |
| 会话标题和侧栏分区 | 标题是 `[<飞书项目空间名>] <会话名>`，会话都归入同名的分区，不置顶。分区里是 7 个 +1，+0 嵌在本序列的 +1 下面，路由和书记员都嵌在入口下面。标题要在 60 个字符以内：空间名太长或带方括号时，在任务文件里写 `pool.label` 另指一个短名 |
| 可写路径和只读路径（`editable_paths`、`protected_paths`） | 空着，交接时提醒 |

### 授权：打印一次清单，不等回复

开场那句话就是授权。将要新建的东西由脚本算出来、打印一次（第 1 步的 `setup.py announce`）：两个空间的名字、知识库节点数、研究任务、会话数和分区名、项目目录里的文件，还有中途要研究员做的事。本会话把清单原样发给用户，这是用户看到的第一条消息；发完接着往下做，不等回复。只有项目名定不出来时，先问一句项目名，见第 1 步。清单不靠本会话自己写：名字和数目跟着任务文件和启用的序列变。

新建以外的动作一律停下问：删除、覆盖、改已有的对象、改分享权限。下面几种情况也停下，把脚本的原话报给用户：

- 同名的飞书项目空间或知识空间有两个以上。
- 同名的项目空间已经有了，约定核对没通过。
- `init --apply` 报告目录里原来就有同名文件，新版本写成了 `.new`。
- 页面上出现升级提示、付费弹窗、权限申请或没见过的对话框。

### hook 生效以后

第 3 步的 `init --apply` 把 hook 写进项目的 `.claude/settings.json`。hook 在本会话里什么时候开始生效，没有实测。生效以后会遇到两件事：

- 项目里的脚本照规定的写法运行，不受影响。写工作项的 `workitem.py` 只有书记员能运行；写文档的 `docs.py` 由负责那份文档的会话运行。本会话两样都不运行。
- 插件目录里的 `setup.py`、`check.py`、`space.py`、`pool.py`、`onboarding.py`：`init --apply` 把它们的路径和内容校验值记进项目清单，hook 照这份记录放行本会话运行它们，bypass 模式下也一样；角色会话运行这几个初始化脚本会被拒绝。命令里的插件路径就写初始化时用的那个绝对路径。插件升级或换了位置以后记录对不上，hook 会拦：默认权限模式下弹确认，请研究员点允许；bypass 和 dontAsk 模式下直接拒绝，这时把第 3 步 `init --apply` 那条完整命令交给研究员在终端里运行一次，记录更新后就恢复。不改写命令去绕开 hook。

### 计时

`onboarding.py` 按阶段计时。第 3 步之前项目里还没有它，用插件目录里的那份，带 `--target`：

```bash
python3.12 -I "$PLUGIN/scripts/onboarding.py" start <阶段> --target <项目目录>
```

```bash
python3.12 -I "$PLUGIN/scripts/onboarding.py" end <阶段> --target <项目目录>
```

第 3 步以后用项目里的副本，在项目目录里运行：

```bash
python3.12 -I .claude/solo-lab/bin/onboarding.py start <阶段>
```

```bash
python3.12 -I .claude/solo-lab/bin/onboarding.py end <阶段>
```

| 阶段 | 归类 | 包住什么 | 谁打点 |
| --- | --- | --- | --- |
| `precheck` | 本机 | 第 1 步的 `check.py precheck` | 本会话 |
| `login` | 等人 | 第 2 步，从发出二维码到读回已登录 | 本会话 |
| `resume` | 等人 | 第 6 步两轮之间，从请研究员回话到他回一句“继续开池” | 本会话 |
| `init` | 本机 | 第 3 步和第 5 步的 `init --apply` | 本会话 |
| `project_space` | 飞书操作 | 第 4 步，从第一次查空间到预览能读到空间，创建空间也在里面 | 本会话 |
| `binding` | 飞书操作 | 第 5 步的 `feishu --live --apply` | 本会话 |
| `sessions` | Claude 平台 | 第 6 步开会话和预登记 | 本会话 |
| `claims` | Claude 平台 | 第 6 步等认领、核对认领 | 本会话 |
| `detach` | Claude 平台 | 第 6 步把会话移到顶层 | 本会话 |
| `section` | Claude 平台 | 第 6 步建分区、归入分区、改标题 | 本会话 |
| `prompts` | Claude 平台 | 等研究员信任目录、点客户端确认框 | 本会话 |
| `nodes` | 飞书操作 | 建知识库节点 | 书记员 |
| `first_task` | 飞书操作 | 登记首条研究任务 | 书记员 |
| `env` | 本机 | 第 7 步 | 本会话 |
| `readback` | 飞书操作 | 第 8 步的补读和 `check --live` | 本会话 |

- 阶段名只能用表里的。脚本里还有一个 `wiki_space`（知识空间的查找和新建）：它和绑定在同一条命令里，分不开，时间记在 `binding` 里，不单独打点。
- 同一个阶段可以记多次。上一次没 `end`，不能再 `start`；不同的阶段可以重叠。
- 只有归类是“飞书操作”的阶段计入 300 秒这个指标。它只是指标，不影响第 8 步的结论。
- 计时命令报错不拦初始化：报错就跳过，接着做。

## 第 1 步：把清单发给研究员，开始计时，前置检查

```bash
python3.12 -I "$PLUGIN/scripts/setup.py" announce --target <项目目录> --name <项目名>
```

这是本会话运行的第一条命令。单独运行，不和别的命令连在一条里。它只读本地文件；输出的第一行是给本会话的话，下面是将要新建的清单。

**运行完先发一条消息，内容就是这份清单，一个字不改。研究员看到的第一条消息应该是它。** 发完不等回复，接着运行下面的命令。

- 照“默认值”定不出项目名的（用户没说项目名，也没说空间的名字）：先不运行这条命令，问研究员一句“这个项目叫什么名字？它也会用作飞书项目空间、知识空间的名字和会话标题的前缀。”，结束本轮。研究员回话以后从这里接着做，这时清单仍是他看到的第一份清单。不写 `--name`、也不写 `--task` 时，脚本报“出错：还没有项目名…”，不会用目录名。
- 用户那句话里还说了别的设置（空间名、会话池的大小、标题前缀、模型）：先照第 3 步把任务文件写好，把 `--name <项目名>` 换成 `--task <项目目录>/solo-lab.task.json`。只启用部分序列的，再加 `--sequences`，和第 3 步的 `init` 写的一样。
- 目录已经初始化过的：脚本照它原来的任务文件算，最后多打印一行“这个目录已经初始化过：…”。
- 报“出错：不在家目录或根目录里初始化…”或“出错：目标目录已有另一运行平台的组织…”：照“项目目录”一节处理，不往下做。
- 报“出错：会话标题的前缀取自飞书项目空间的名字…”：名字超过 40 个字，或者带方括号。照第 3 步把任务文件写好，在 `pool.label` 里写一个不带方括号的短前缀，改用 `--task`。

```bash
python3.12 -I "$PLUGIN/scripts/onboarding.py" begin --target <项目目录>
```

重复运行不会重置起点。上一次初始化已经结束的，这次记成“补齐”，和首次分开。

```bash
python3.12 -I "$PLUGIN/scripts/check.py" precheck
```

打点：`precheck`。它逐项打印“通过、提醒、失败、跳过”，最后一行是“预检：没有失败项。”或“预检：N 项失败。”。

- “lark-cli 用户身份”或“meegle 登录”失败：做第 2 步。
- 版本太低、诊断上报这类要升级或改设置的：把命令给研究员，由他本人执行，不代跑。
- “飞书项目权限”是提醒、说明写着“这个账号还看不到任何空间”：接着做，第 4 步用模板建出项目空间。
- 其余各项的含义和处理办法见 `references/precheck.md`。

## 第 2 步：登录

前置检查里登录都通过的，跳过这一步。

```bash
python3.12 -I "$PLUGIN/scripts/setup.py" login
```

它给登录失效的那个命令行发起设备码登录，两个都失效就各发起一次。每个命令行打印三行：“<命令行>：请研究员扫码或打开链接授权，N 分钟内有效。”、二维码图片的路径、链接。把图片和链接交给研究员，开始给 `login` 打点。设备码不打印，本会话不接触密码、验证码和令牌。

研究员说扫好了，或者过一会儿，读回登录状态：

```bash
python3.12 -I "$PLUGIN/scripts/setup.py" login --wait
```

| 输出 | 怎么办 |
| --- | --- |
| “<命令行>：已登录。” | 结束 `login` 打点，接着做 |
| “<命令行>：还没授权，二维码还有 N 分钟有效；…” | 提醒研究员扫码，再运行一次 `login --wait` |
| “<命令行>：授权超时，这次的二维码作废；重新运行 setup.py login。” | 从 `setup.py login` 重来 |
| “出错：<命令行> 的设备码登录没发起成…” | 这个命令行的登录请研究员在自己的终端里做，做完重跑第 1 步的前置检查 |

- `--wait` 最多等 300 秒。运行命令的超时比它短时，加 `--timeout <秒数>`，没等到就再运行一次。
- 不直接运行 `lark-cli auth login` 和 `meegle auth login`：登录只走 `setup.py login` 这一个入口。项目初始化以后，直接运行它们会被项目权限和 hook 拒绝。
- 以后角色会话报“登录过期”，也回到本会话做这一步。角色会话运行 `setup.py login` 会被 hook 拒绝。

## 第 3 步：写任务文件，生成项目文件

任务文件只放脚本和 hook 要用的几项，不写研究内容。照“默认值”写成 `<项目目录>/solo-lab.task.json`：

```json
{
  "name": "<项目名>",
  "description": "<一句话描述>",
  "feishu": {
    "meegle_space": "<飞书项目空间名>",
    "wiki_space": "<知识空间名>"
  }
}
```

- 必填的只有 `name`、`description` 和 `feishu.meegle_space`。
- `name` 照“默认值”定，用户只给了空间名的就是空间名。`feishu.meegle_space` 写用户指定空间时用的原话，可以是名字、simple_name 或 project_key；`CLAUDE.md` 和 `feishu/README.md` 在绑定以后显示空间在飞书里的名字。
- `feishu.wiki_space` 不写就用项目名。
- 用户说了别的设置才加别的项：`editable_paths`、`protected_paths`、`models`、`pool`（`p1`、`p0`、`later`、`max_sessions`、`label`）、`feishu.template_url`。格式见 `$PLUGIN/scaffold/task.example.json`。
- 目录已经初始化过的（有 `spec/task.json`）：不重写任务文件，`--task` 指原来的任务文件；找不到原文件就指 `spec/task.json`。

```bash
python3.12 -I "$PLUGIN/scripts/setup.py" init --target <项目目录> --task <项目目录>/solo-lab.task.json --apply
```

打点：`init`。看两处：

- 最后一行“已写入 N 处。”。同样的输入再运行一次，是“已写入 0 处。”。
- “合计”一行。里面有“本地改过，新版本写 .new”或“内容不同，.new 已存在”，说明目录里原来就有同名文件，脚本没有覆盖它。把这些文件列给用户，停下，请他对照合并。`CLAUDE.md` 和 `.claude/settings.json` 没合并以前不开池：会话读不到组织规则，hook 也没装上。

输出里的“提醒：任务文件没有写 editable_paths…”“提醒：任务文件没有写 protected_paths…”记进交接。“提醒：项目还没绑定飞书空间”是下两步的事。

### 写完以后：请研究员信任这个目录

`init --apply` 往目录里写了 hook 和权限规则。桌面应用要研究员信任这个目录，才让会话在里面开出会话；没信任时，第 6 步开出来的会话都显示 “Couldn't start: This workspace isn't trusted”，在失败的会话里点 Try again 也不弹信任框。空目录最容易遇到：研究员打开它的时候里面没有东西，应用不问，也不留信任记录。

`init --apply` 的输出末尾要是有“注意：没有查到研究员信任这个目录的记录。…”，在这里停下，不做第 4 步：

1. 运行 `python3.12 -I .claude/solo-lab/bin/onboarding.py start prompts`。
2. 结束本轮。最后一句只说这一件事：请研究员信任这个目录。做法照输出里写的：在侧栏点开本会话，应用提示这个目录还没有受信任时选 Trust workspace；没有提示的话，在桌面应用里新建一个会话、目录选本项目，应用会问。
3. 研究员回话说信任过了，运行 `python3.12 -I .claude/solo-lab/bin/onboarding.py end prompts`，接着做第 4 步。

没有这段“注意”，不用停：脚本查到了信任记录，或者本机的记录文件读不出来（这时它不下判断，开出来的会话要是报 “This workspace isn't trusted”，照第 6 步的表回到这里）。信任是研究员的批准：会话不替他改设置，不想办法绕开。脚本读的是本机的信任记录，查不到也可能是应用把它记在了别处，所以研究员说信任过了就接着做；真没信任的话，第 6 步的开池清单开头还会再提醒一次。

停在这一步而不是第 6 步，是因为第 4、5 步要在飞书里新建空间：应用这一侧不通的话，什么都还没建。

`init` 还生成一份最小研究任务单草稿 `packages/drafts/pmo/研究任务单-首条.md`，第 6 步由书记员登记；已经有这份草稿就不动它。只启用部分序列用 `--sequences`，项目管理和质量必须启用。生成了哪些文件、各自管什么，见 `references/mechanisms.md`。

## 第 6 步：开池

```bash
python3.12 -I "$PLUGIN/scripts/pool.py" open --target <项目目录>
```

只读。第一行是“开池清单：<项目名>（共 12 个会话，总上限 30）。会话标题的前缀和侧栏分区的名字：<分区名>”。下面按批列出本会话要开的 7 个 +1，每个带 name、title、model、prompt、background 和 expect，后面缩进列出它下面的会话。

会话按委托的方向开：本会话开各序列的 +1，+1 在首轮里开出本序列的 +0。侧栏里谁开出的会话就嵌在谁下面，所以开完以后各序列是 +1、+0 两层。入口 `PMO-p1` 下面是路由 `PMO-p0-router` 和书记员 `PMO-p0-ledger`，两个平级。+0 不开会话，+0 之间不分上下级。

开池不碰飞书：每个会话开局只认领，书记员也一样。会话池开齐以后，书记员的两件初始化写入单独做，见“书记员的两件初始化写入”。

清单开头要是有“注意：没有查到研究员信任这个目录的记录。…”：回第 3 步的“请研究员信任这个目录”，他说信任过了再开。

清单开头要是有“注意：本会话是 bypass 模式。…”：bypass 模式下应用对每一次开会话都要研究员点一次确认，卡片弹在发起的那个会话里，这是应用有意留的确认，不去绕开。照清单写的办：

- 它给出两种做法的：先不开池，把两种做法原样告诉研究员，结束本轮等他选。他选换 auto 模式，本会话到此为止，新会话从开池接着做；他选留在本会话，接着往下开。
- 它写“接着在本会话开”的：已经有会话开出来了，不换模式。告诉研究员每开一个会话要到弹卡片的那个会话里点一次，然后接着开。
- 研究员没点之前，那个会话停在等确认，`--wait` 会超时并列出还差谁。这时提醒研究员去点，再重跑一次 `--wait`。

### 默认档：本会话分批、分轮开 +1

应用对会话自己开出的会话（+1 开的 +0、入口开的路由和书记员）有两条上限，所有序列合在一起算：

- 同时最多 5 个在跑。到了上限，应用回“Not started: 5 sessions the app started on its own for this work are still working, the most it runs at once.”。
- 研究员每发一条消息以后，最多开出 10 个。到了上限，应用回“Not started: For this work the app starts at most 10 sessions without a card after each message from the user, 5 of them working at once, and it can't start another now.”。

本会话在研究员亲口开始的这一轮里开的 +1 不算在里面。

所以清单把 7 个 +1 分成几批，批再分成几轮，一轮对应研究员的一条消息。一批下面要开的会话不超过 5 个；一轮下面要开的不超过 8 个，留 2 个余量。默认的 12 个会话是 1 批、1 轮，不用研究员回话；任务文件把 `pool.later` 改短、把 `pool.p0` 调大，开得更多时才会分批、分轮，比如六个序列各开两个 +0、共 21 个会话是 4 批、2 轮：第 1 轮开第 1、2 批，第 2 轮开第 3、4 批。

分批是为了不让一个 +1 要开的会话全被拒。撞了“同时 5 个”的会话，要等它自己开出的会话回话、应用再叫醒它的时候才补开；一个都没开成的 +1 没有会话回来叫醒它，只能请研究员到它的会话里说一句话。

每一批做四件事，顺序不能换：

1. **开会话**（打点：`sessions`）。用 `start_session` 把这一批的 +1 都开出来。`initiation` 写 `user_asked`，`context` 写 `fresh`，`use_worktree` 写 `false`，权限模式不填；`name`、`title`、`model`、`prompt`、`background` 照清单原样填。`background` 不足 80 个字符会被工具拒绝，清单里的都够，不要删减。
2. **移到顶层**（打点：`detach`）。马上对这一批的 +1 各调一次 `detach_session`，它们就和本会话同级。+1 要等预登记才能认领，认领以后才往下开，所以这一步排在预登记前面：它开出下一级的时候已经在顶层了。
3. **预登记**（打点：`sessions`）。拿第 1 步返回的会话 ID，逐个运行清单里的 expect：

   ```bash
   python3.12 -I .claude/solo-lab/bin/pool.py expect <会话名> --role <角色> --desk <开会话时返回的会话 ID>
   ```

   输出“已预登记 <会话名>（<角色>），桌面会话 <ID>。对方运行 pool.py claim 时转正。”就登记上了。
4. **等这一批**（打点：`claims`）。Bash 的超时给 240000 毫秒：

   ```bash
   python3.12 -I "$PLUGIN/scripts/pool.py" open --target <项目目录> --wait 180 --batch <第几批>
   ```

   它等到这一批的会话都认领、首轮都结束才返回，最后一句写明下一步：接着开哪一批，“这一轮到此为止”，或者“这是最后一批”。返回 1 是超时，输出里列着谁没认领、谁的首轮还没结束。有首轮还没结束的，重跑这条命令再等一次，它们在跑的时候占着名额；只是没认领的不用等，接着开下一批，没开出来的最后一并处理。

**一轮开完，停下等研究员回话。** `--wait --batch` 的最后一句是“这一轮到此为止…请研究员回一句“继续开池”…”时，不要接着开下一批：下一轮的 +1 现在开出来，它们下面的会话会被应用拒绝。做三件事：

1. 运行 `python3.12 -I .claude/solo-lab/bin/onboarding.py start resume`，开始记等研究员回话的时间。
2. 结束本轮。最后一句只说两点：已经开出几个会话；应用在研究员的一条消息以后只让会话自己开出 10 个会话，请他回一句“继续开池”。
3. 研究员回话以后，先运行 `python3.12 -I .claude/solo-lab/bin/onboarding.py end resume`，再开下一轮的第一批。

入口 `PMO-p1` 在第 1 批。

+1 以下的会话不用本会话开，也不用本会话预登记：每个会话的认领输出里有一张表，写着它要开出哪些会话、每个的参数和 expect 命令，它在首轮里照表开。

最后一批等完，接着做“全部开完以后”。

实测过的客户端规则（2026-11-12）：

- 被别的会话开出来的会话，在首轮里可以再开会话，可以连续接力两跳；它被移到顶层以后也可以。
- 这样开出来的会话，应用同时最多让 5 个在跑。做初始化的那个会话开出的全部会话合在一起算，把 +1 移到顶层也不分开算：4 个移到顶层的会话各自往下开，第 6 个、第 7 个被拒。
- 研究员每发一条消息以后，这样开出来的会话最多 10 个：一次真实初始化里前 10 个都开出，第 11 个、第 12 个被拒。本会话亲手开的 +1 不算。
- 被别的会话的消息叫起来的那一轮，应用拒绝开会话，报“Start sessions only on the user's own words to you here…”。所以下一级没开出来时，给上一级发消息没有用。
- 把一个会话移到顶层，它下面的会话还嵌在它下面：在三层的试验会话上移了第一层，第二层、第三层的上一级没有变。
- 嵌着的会话在侧栏分区里照样一层一层缩进显示。

2026-11-23 在桌面应用 6.28899.6 上用测试目录重测了三轮（5 个、15 个、21 个会话，都不绑定飞书）：

- 两条上限的数字都没变，拒绝时的原话也没变。本会话亲手开的 +1 还是不算。
- 7 个 +1 一次全开、下面要开 14 个会话时：前 5 个开成，后面的被“同时 5 个”拒绝。已经开成一个会话的 +1，那个会话回话时被应用叫醒，自己把剩下的补开了；两个都被拒的 +1 一直停着。
- 下面的会话累计开到 10 个以后，第 11 个被“每条消息 10 个”拒绝。
- 被别的会话的消息叫起来的那一轮还是开不了会话。
- 会话的认领可以由 hook 完成，所以认领表里有名字不代表它自己跑通了认领命令：有一个会话的认领命令被它自己的权限检查拒绝，表里照样显示已认领，它没拿到角色说明。

`detach_session` 的工具说明里写着另外两条：嵌在别的会话下面的会话，随上面那个会话一起归档；移到顶层的会话结束一轮时，开它的会话不再被叫醒。

| 情况 | 怎么办 |
| --- | --- |
| 第 1 个会话就开不出来 | 走回退档 |
| 中途某一个 +1 开不出来 | 记下名字，接着开别的，最后一并报给用户 |
| `detach_session` 失败 | 这个 +1 留在本会话下面，照常预登记；交接时告诉研究员不要归档本会话，它下面还挂着会话 |
| `model` 填不进去 | 不填，开好以后告诉用户哪几个要改模型 |
| 某个会话回话说应用拒绝了启动（“Not started: …”） | 它撞了上面两条上限里的一条。不要让它改提启动卡；批次和轮次都做完以后，请研究员点开它，说一句“照认领输出开出下一级”，研究员亲口说的那一轮不占名额 |
| `--wait --batch` 列着某个会话没认领，它的上一级已认领 | 上一级首轮没把它开出来。接着开下一批；批次都开完以后，请研究员点开上一级的会话，说一句“照认领输出开出下一级”：研究员亲口说的那一轮它能开 |
| 过了一两分钟某个会话还是“待转正” | 给它发一条消息，请它重新运行 prompt 里的认领命令。子会话等预登记最多 60 秒，超时会报“没有找到本会话认领 … 的许可” |
| 子会话显示 “Couldn't start: This workspace isn't trusted” | 目录还没受信任。回第 3 步请研究员信任这个目录；信任以后请他在每个失败的会话里点 Try again，开局的任务还留着，不用重新开 |
| 某个会话回话说认领命令被权限检查拒绝了 | 认领表里有它的名字，是 hook 记的，它没拿到角色说明。开它的会话会把这件事记进研究员任务清单（`pool.py show` 末尾列着）：请研究员到那个会话的窗口里说一句允许，或者自己在终端里跑那条命令。不替它跑，不让别的会话代跑 |
| 子会话停在权限确认框上 | 请研究员到侧栏点开它处理，这段时间记 `prompts` |

### 全部开完以后

最后一批的 `--wait --batch` 返回以后，做下面三件事，再做“书记员的两件初始化写入”。

1. **归入分区**（打点：`section`）。`list_sections` 里找名字等于分区名的，没有就用 `create_section` 建一个。调一次 `move_sessions`，`session_ids` 写 7 个 +1 的 ID 再加 `self`，`section_id` 写分区的 ID。嵌在 +1 下面的会话跟着它移动；单独移动它们会被拒绝，报“nested sessions move with their parent”。默认权限模式下移动别的会话要研究员点一次确认。`move_sessions` 失败或被拒：给每个 +1 发一条消息，请它用 `move_sessions` 把自己（`self`）归入这个分区，移动自己不用确认。
2. **等全部认领**（打点：`claims`）。Bash 的超时给 300000 毫秒：

   ```bash
   python3.12 -I "$PLUGIN/scripts/pool.py" open --target <项目目录> --wait 240
   ```

   它每 5 秒看一次认领表，等到清单里的会话都认领、首轮都结束才返回，不看飞书。返回 0 时第一句是“会话池已开齐：12/12 条认领。”，后面写着下一步：做书记员的两件初始化写入；项目还没绑定飞书的，写“只开会话池的到此为止”。返回 1 时照输出办：

   | 输出 | 怎么办 |
   | --- | --- |
   | “…还有 N 个没认领”，下面逐个写着由谁开出、上一级认领了没有 | 上一级已认领的，是它首轮没把下一级开出来：请研究员点开上一级的会话，说一句“照认领输出开出下一级”，再重跑这条命令 |

### 书记员的两件初始化写入

会话池开齐以后做，由本会话发给书记员。项目还没绑定飞书空间的，这一步先不做。

```bash
python3.12 -I "$PLUGIN/scripts/pool.py" open --target <项目目录> --writes
```

它打印书记员的会话名、桌面会话 ID 和要发的一段话。用会话管理工具 `send_message` 把这段话原样发给书记员，它接着做两件事：

1. `docs.py ensure-node all --apply`：在知识空间里建 22 个节点。已经有同名节点的直接用，不再建。
2. `ledger.py query tasks`：空间里已经有研究任务就跳过；没有就登记首条研究任务，三条命令依次跑：`docs.py upload packages/drafts/pmo/研究任务单-首条.md --apply` 传文档，`workitem.py register packages/drafts/pmo/研究任务单-首条.md --apply` 建工作项，`docs.py relink <工作项 ID> --apply` 把工作项 ID 写回文档。别的包是作者上传、书记员登记；这一份是初始化生成的，没有作者，三步都由书记员做。

两件各用 `nodes`、`first_task` 打点。发完等它做完（打点：`claims`），Bash 的超时给 300000 毫秒：

```bash
python3.12 -I "$PLUGIN/scripts/pool.py" open --target <项目目录> --writes --wait 240
```

它等到书记员这一轮结束、知识库节点都在才返回。返回 0 时写着“…首条研究任务已登记（#…）”；写“没有首条研究任务的登记回执”的，空间里原来就有研究任务属正常，第 8 步的 `check --live` 会核对。

本会话不替书记员写：工作项的写命令只有唯一认领的书记员能运行，首条研究任务单的上传也归它。要看它回了什么，用会话管理工具 `list_events` 读它的会话。

## 第 8 步：补读流程，四层检查

打点：`readback`，包住本步的两条命令。

流程图只能从一条工作项读出来。首条研究任务登记以后重读一次，正式实验流程的节点、负责角色和必填项才进 `feishu/space.md` 和 `org/phases.md`：

再取会话列表：调 `list_sessions`，`include_archived` 写 `true`，`limit` 写 200。把返回的 JSON 数组原样存成一个文件，放在系统临时目录里，不放进项目目录。

然后回读每个会话实际用的模型、推理强度和窗口。会话列表里工作目录是项目目录、没归档的会话，逐个调一次 `get_session` 和一次 `get_usage`，`session_id` 填它的 `sessionId`；本会话也各调一次，`session_id` 写 `self`。都是只读调用，19 个会话共 38 次。从 `get_session` 取 `model` 和 `effort`，从 `get_usage` 的 `context` 取 `contextWindow`；`context.status` 不是 `ok` 或者调用失败的，那一项写 `null`。存成一个回读文件，和会话列表放在一起：

```json
{"self": {"model": "claude-fable-5-2", "effort": "xhigh", "contextWindow": 1000000},
 "sessions": [{"sessionId": "local_...", "model": "claude-opus-5-5", "effort": "xhigh", "contextWindow": 1000000}]}
```


| --- | --- | --- |
