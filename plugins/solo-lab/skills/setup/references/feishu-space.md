# 飞书空间：约定、绑定和快照

## 三层

飞书项目模板和插件各自发版。插件不内置空间的结构，运行时读空间；脚本要按含义处理的东西事先约好。对接分三层：

| 层 | 内容 | 在哪里 | 谁写 |
| --- | --- | --- | --- |
| 约定 | 脚本按含义处理的槽位：5 个类型，18 个字段，9 个角色，各类型要有的状态，归档节点、签字关和冻结核对的规则，参考模板的链接 | 插件的 `orgspec/contract.json`，项目里的副本在 `.claude/solo-lab/orgspec/` | 插件 |
| 绑定 | 每个槽位对应这个空间里的哪个类型、字段、角色和状态 | 项目的 `feishu/ids.json` | `setup.py feishu --apply`，只在研究员的会话里运行 |
| 流程和表单 | 有哪些流程、节点怎么排、每一步谁负责、必填什么、新建时必填什么 | 只在飞书空间里。读出来的快照在 `feishu/space.json` 和 `feishu/space.md` | 模板 |

- 槽位以外的字段，脚本按名字读写。模板加字段、改流程、改必填项而槽位都在时，插件不用改。
- 绑定是台账脚本信任的东西，写入口只有一个。角色会话可以读空间、重读快照，不写绑定。
- 没绑定以前，台账脚本不读也不写飞书。

## 项目空间从哪来

每个项目一个空间，名字写在任务文件的 `feishu.meegle_space`，默认等于项目名。

- 空间不存在：初始化会话用模板创建，做法见 `create-space.md`。
- 空间已经有了：直接绑定。它要是用模板建出来的、符合约定的空间；对不上的地方用技能 `solo-lab:space-bind` 处理。
- 搭建和修改模板不在初始化里。空间缺类型、字段、角色或流程时，把缺项报给模板维护者。模板的说明、结构和搭建手册在插件仓库顶层的 `feishu-template/`。
- 项目空间是创建那一刻照模板建出来的。模板以后的改动会不会进到已有的空间，没有验证，按不会处理。

## 绑定

```bash
python3 -I "$PLUGIN/scripts/setup.py" feishu --target <项目目录> --live
```

```bash
python3 -I "$PLUGIN/scripts/setup.py" feishu --target <项目目录> --live --apply
```

不加 `--apply` 是预览：只读飞书，不写文件，末尾打印 `feishu/binding.md` 的全文。它读的是项目里的 `spec/task.json`，所以要先做过 `init --apply`。

**找空间。** 每次都按任务文件写的空间去飞书精确查找，名字、simple_name、project_key 都认。一个都没有就报错，给出模板链接；正好一个就用它；两个以上停下，列出各自的 simple_name 和 project_key。名字可能换了指向，key 不会，所以每次都查。

**读结构。** 读约定里那几个类型的字段和选项、角色、新建时的必填字段、状态和流程。每个流程从它的一条工作项读出节点、负责角色和必填项。

**填槽位。** 每个槽位按下面的顺序找，正好对上一个才算绑上：

1. `--map` 指认的。
2. 上次绑定记下的键，它在空间里还在。
3. 标识：类型认系统标识，角色认角色 id，字段认对接标识。命令行只读得到新建页上那些字段的对接标识。
4. 名字。状态没有标识可认，只按名字找。

**核对流程。** 每个流程正好一个末尾节点，由书记员负责；每个节点正好一个约定里的角色；签字字段和结论字段在某个节点上是必填。还没有工作项的流程读不到节点，只提醒，不算问题。

**写入。** `--apply` 写这几样：

| 文件 | 内容 |
| --- | --- |
| `feishu/ids.json` | 空间的 project_key、simple_name 和名字，各槽位绑到的键，绑定时间 `bound_at`，约定的版本，研究员的 open_id，知识空间的 space_id |
| `feishu/space.json`、`feishu/space.md` | 空间结构的快照，前一份给脚本用，后一份给人看 |
| `feishu/binding.md` | 绑定结果、要处理的问题、提醒、还缺的知识库节点、读回的几项 |
| `org/phases.md` | 研究任务各流程的节点、负责角色和必填项 |

- 输出里“约定核对（contract_version 1）：通过”才算空间符合约定。有问题时写着“N 个问题，见 feishu/binding.md 的“要处理的问题””。
- 还有没绑上的槽位也能写入：用到它的台账命令会停下报错，绑上以后就能用。一种类型都没绑上时只记下空间和 open_id，不写绑定时间，台账脚本照样不读写飞书。
- 名字不同的类型和字段用 `--map` 指认，写法和判断办法见技能 `solo-lab:space-bind`。角色、状态和流程指认不了，只能改空间。
- 绑定写入以后重跑一次 `init --apply`，`CLAUDE.md`、`feishu/README.md` 和开池清单才带上空间的标识。

## 快照什么时候重读

流程图只能从一条工作项读出来。新空间里没有工作项，绑定时每个流程都提醒“还没有工作项，流程图读不到；登记第一条以后重读”。

| 什么时候 | 谁 | 命令 |
| --- | --- | --- |
| 首条研究任务登记以后 | 初始化会话 | `setup.py feishu --target <项目目录> --live --apply`，`org/phases.md` 一起更新 |
| 某个流程登记了第一条工作项，或者空间配置改过 | 任何会话 | `python3 -I .claude/solo-lab/bin/space.py snapshot --target . --apply`，只更新快照，见技能 `solo-lab:space-read` |
| 状态改名、槽位有增减 | 研究员的会话 | 重新绑定：`setup.py feishu --live`，核对后加 `--apply` |

推进节点时 `ledger.py` 每一步都现读这条工作项的节点，不依赖快照。快照用来把字段名和选项名换成空间里的键，也用来讲清空间。

## 知识空间和节点

每个项目一个知识空间，名字写在任务文件的 `feishu.wiki_space`，不写就用项目名。

- `setup.py feishu --live` 翻完研究员能看到的全部知识空间再判断。正好一个同名的就记下 space_id；没有同名的，预览时只提示，`--apply` 时新建；两个以上不自动选，停下请研究员定。
- 节点骨架是 21 个：研究任务、同序列需求包、跨序列需求包、决策包、反馈包、汇报文档、归档文档这 7 个一级节点，同序列需求包和归档文档下面各 7 个序列节点。
- 节点由书记员建：`ledger.py ensure-node all --apply`，先建一级节点，再建各序列的节点，结果写进 `feishu/ids.json`。上一级下已经有标题相同的节点就直接用，不再建；重跑不会重复建。
- 已有的节点只是名字不同的，先请研究员在网页上改成清单里的名字，否则会另建一个。命令行没有给节点改名的命令，节点标题跟着节点文档的一级标题走。
- 各个包的文档等书记员登记时才建。归档时主文档的整棵子树移到“归档文档”下对应的序列，移动的是原节点，链接不变。

## .env

```bash
python3 -I "$PLUGIN/scripts/setup.py" env --target <项目目录> --apply
```

它在项目目录的 `.env` 里写两行，方便研究员和别的工具找到这两个地方：

```text
# solo-lab：由 feishu/ids.json 生成
FEISHU_PROJECT_URL=https://project.feishu.cn/<simple_name>
FEISHU_WIKI_URL=https://<租户域名>/wiki/space/<space_id>
```

- 两行都从 `feishu/ids.json` 生成，脚本读绑定仍然只认 `ids.json`。重跑只换这两行；`.env` 里的其他行不动，也不显示。只写链接，不写令牌和密码。
- 租户域名在书记员建出第一篇文档时才记进 `ids.json`，所以这一步排在首条研究任务登记之后。
- `setup.py check` 的“飞书”一层核对这两行在不在、和 `ids.json` 对不对得上。

## 换空间

已经绑定过的项目改用另一个项目空间，比如原来的空间建错了。项目进行中尽量不换：插件搬不了工作项。

1. **准备新空间。** 用模板创建。绑定之前可以先只读核对一遍，最后一行是“这个空间符合约定：用它建出来的项目空间，绑定不用 --map。”才往下做：

   ```bash
   python3 -I "$PLUGIN/scripts/setup.py" template --space <新空间的名字、simple_name 或 project_key>
   ```

2. **改任务文件。** `feishu.meegle_space` 写新空间。新旧空间同名时写新空间的 simple_name 或 project_key，不写名字。重跑 `init --apply`。
3. **预览。** `setup.py feishu --live` 打印“换空间：旧空间…→ 新空间…”，`feishu/binding.md` 多出“换空间”一节，列出两个空间的名字、simple_name 和 project_key，以及旧空间里还有没有工作项。
4. **旧空间里有工作项就先停。** 在新空间重建会换掉工作项 ID，本地的回执、草稿和会话名里的 ID 指的都是旧空间。旧空间留作档案，台账以后不再读写它；没办完的工作项要不要在新空间重建，由研究员逐条决定。研究员确认以后，写入时加 `--leave-old-items`。旧空间没查成的，也要加这个参数才写入。
5. **写入。** `feishu/ids.json` 的 `previous_spaces` 记下旧空间的 key、名字、原来的绑定时间、换出的时间和留在旧空间的工作项类型。写入后重跑一次 `init --apply`。

- 任务文件里的名字查不到、而它正是上次绑定的空间名：按空间在飞书里改了名处理，接着用上次的 key，并提醒把任务文件改成新名字。
- 任务文件写的空间和绑定的不一致时，台账脚本停下，等重新绑定。
- 换项目空间不换知识空间，知识库节点照旧。旧空间留不留由研究员决定，删空间只能他本人做。

## 插件不配置视图

初始化和各角色都不建、不改、不查视图，空间里有哪些视图不影响就绪判定。读台账只走 `ledger.py` 的条件查询：`queue`、`blocked`、`verifying`、`open`、`cross`、`tasks`、`recent` 和 `source:<ID>`。

## 命令行上的坑

下面这些行为是在真实空间上测到的，脚本已经照着处理，手工排查时用得上：

- 流程图要从一条工作项读：`workflow get-node`。一个类型有哪些流程，从 `template` 字段的选项读出；有哪些状态，从 `work_item_status` 字段的选项读出。
- `workitem meta-fields` 每页 50 个，`workflow get-node` 每页 20 个，读结构要翻页。`meta-types` 也列出停用的系统类型。
- `meta-fields` 把多行文本报成 text，和单行文本一样，约定核对分不出这两种。
- 新建工作项时 `field_value` 一律传字符串，日期传毫秒时间戳的字符串，传数字会被拒绝。空字符串能清空文本、数字、链接、单选和日期字段。
- 日期字段写目标日期的 UTC 中午。网页按浏览者的时区显示，这样 UTC-12 到 UTC+11 的人看到的都是同一天。
- 确认节点缺必填项时，飞书的报错只报第一个缺的字段。要列全，用 `workflow list-state-required --mode unfinished`。还没走到的节点确认不了，字段可以提前填。
- 回滚必须写原因。回滚以后已填的字段值还在，所以 `ledger.py` 回滚时把被退回各步的必填字段清空。
- 操作记录有延迟，刚发生的操作几秒到一两分钟内查不到；节点和工作项的读取是即时的。
- 每个类型都自带“开始”“已终止”两个系统状态。MQL 不会自动排除已终止的工作项，`ledger.py` 的查询都显式排除。终止工作项命令行做不了，要在网页上做。
- MQL 的表名认 type_key 或类型现在的名字，不认系统标识。判空用 `IS NOT NULL`，清空成空字符串的字段算空。
- `workitem get` 不返回人员字段的值，`ledger.py` 改用 MQL 读，只取名字。
- 工作项的网页链接是 `https://project.feishu.cn/<simple_name>/<类型的系统标识>/detail/<工作项 ID>`，simple_name 和 project_key 不能互换。
- “来源工作项”“所属研究任务”用单行文本存工作项 ID。
- lark-cli 只读当前目录、`/tmp`、`~/files` 下的 `@文件`，所以 `ledger.py` 一律用 `--content -` 从标准输入传正文。
- `docs +create` 只返回 docx 链接和 document_id，要用 `wiki +node-get` 换出知识库节点，主文档字段存 `/wiki/` 链接。
- 所有会话用的是研究员一个飞书账号，飞书分不出是哪个会话在写，谁能写由 hook 管。

## 没实测、先按推测处理的

| 假设 | 不成立时 |
| --- | --- |
| 用模板建出来的空间通过约定核对，标识和模板相同 | 见 `create-space.md` 的“没验证过的” |
| `https://<租户域名>/wiki/space/<space_id>` 能打开知识空间首页 | 改用知识空间根节点的链接；脚本现在只生成前一种 |
| 研究员不是空间管理员时，没有负责人的节点也能确认 | 研究员是管理员时测过能确认。空间一般是研究员自己建的，就是管理员 |
| 修正“关联工作项”（`ledger.py relink`）在真实空间上照常工作 | 只有离线测试，第一次用时先预览，再在测试项上执行。别的涉及飞书文档的台账命令都在真实空间里走通过：登记时建主文档、交付包上传、归档移动文档、本地文件直接上传 |
