# 需求文档、评测协议、实验规格和实验方案

验证流程靠管住测量把关：Eval Set 和阈值在出结果之前定下，由研究员签字后冻结；正式分数只由质量序列在冻结的 Eval Set 上跑出；结论只对照签过字的阈值。第 3–5 步把这些东西写成文档，交研究员签字。

| 步 | 节点 | 负责 | 配合 | 写什么 |
| --- | --- | --- | --- | --- |
| 3 | 准备 PRD 和 Eval Set | 产品 +2 | 质量 +2：建并冻结 Eval Set，写评测协议 | 需求文档 `spec/requirements.md`；评测协议 `spec/eval-protocol.md`；Eval Set 和它的版本 |
| 4 | 确定假设条件 | 算法 +2 | 质量 +2：核对阈值 | 实验规格 `spec/spec.md`，含“假设和阈值”一节和波动估计；总预算 |
| 5 | 设计实验方案 | 算法 +2 | 无 | 实验方案 |

- 每一步完成时必填什么，以飞书空间为准：`python3.12 -I .claude/solo-lab/bin/ledger.py next <研究任务 ID>` 现读，流程对照在项目的 `org/phases.md`。
- 研究问题、目标和成功标准写在研究任务单里，这几份文档引用它，不重复。
- 配合方的活，由负责这一步的 +2 发跨序列的需求包去请，不拆并行的步骤。
- 文档写在本地。要填进研究任务链接字段的（需求文档、规格、实验方案），负责这一步的 +2 请书记员上传：登记请求里把字段写成 `<字段>=@<本地文件>`，书记员确认节点时把文件传到研究任务单下面并填上链接。研究员签字前要看的，先请书记员用 `workitem.py update <任务 ID> --set <字段>=@<本地文件>` 传上去，把链接写进决策包。文件改过再传是一篇新文档、新链接，所以签字以后冻结的字段不会悄悄变。委托给 +1 去查、去整理的产出，验收通过以后用它交付包文档的链接。产出齐了，负责这一步的 +2 给书记员发登记请求确认节点，写明各必填字段的值。

## 谁来写、在哪里写

- 研究任务走到第 3、4、5 步时，这一步的负责序列 +2 用本技能起草；质量 +2 接到跨序列的需求包后，用本技能写评测协议。
- 研究员可以直接点开这个 +2 的会话谈。谈定的事由这个 +2 写成决策包交给入口，没写进台账的决定不算数。
- 被其他 agent 会话叫醒的轮次不向研究员提问：把问题写进决策包，交给入口。

## 怎么写

`spec/` 下的三份文档，初始化脚本已经按模板生成了草稿。

1. **先查，再问。** 动笔前把能查的查完：研究任务单、代码库的目录和入口、评测脚本、数据文件和规模、git 历史、已有的运行记录。评测数据放在项目目录以外的，查清放在哪个系统、ID 和现在的版本。每节要弄清什么、先去哪里查，见 `references/questions.md`。
2. **写草稿。** 按模板的小标题写，每条句末标来源：
   - 〔研究员确认〕：研究员说过或确认过的。
   - 〔查到：<文件路径或命令>〕：从代码、数据或存放数据的系统里查到的，写明在哪里查到。
   - 〔推测，待确认〕：查不到、也还没问的。没把握的不要写成确定的样子。初始化时从旧版任务文件填进来的句子也标成这样，同样要问清。
3. **只问查不到的。** 把标〔推测，待确认〕的条目整理成问题，一次问三五个，附上你的推测和理由，请研究员确认或改正。不发长问卷，不问代码里查得到的事。
4. **改到没有〔推测，待确认〕，再请研究员签字。** 签字都走决策包，写法见 `solo-lab:packages`。

## 第 3 步：需求文档和 Eval Set

**需求文档。** 产品 +2 起草，写在 `spec/requirements.md`：要解决的问题和目标用户、现状工作流和基线、成功判据、约束、停止条件、试点方案。成功判据要和研究任务单的成功标准对得上；判据要改，先回研究任务单。

**Eval Set 和评测协议。** 这两样由质量序列做。产品 +2 发跨序列的需求包，请质量 +2 建并冻结 Eval Set、写评测协议；质量 +2 交付 Eval Set 的版本和评测协议。

- Eval Set 分开发集和正式集，评测协议的模板里写作 dev、test。实验方只碰开发集；正式集只由质量序列持有，每一轮只跑一次。划分规则写进评测协议的“划分和可见性”。
- 评测协议写在 `spec/eval-protocol.md`：数据、存放和版本、划分和可见性、接入方式、打分、重复和不确定性、证据标准。能执行的部分写成脚本，或者用固定版本的数据和配置，协议里写说明并指向它们。
- 冻结就是把版本定死：每份数据写明放在哪、校验和或固定的版本号，Eval Set 给一个版本号。这个版本号填进研究任务的“评测集版本”字段。
- 评测协议在优化过程中保持不变，要改由质量序列提出、研究员签字。

**签字。** 第 3 步不单独签字。验证流程研究员只在第 4 步和第 9 步签字：需求文档、评测协议和 Eval Set 的版本随第 4 步的签字一起冻结，第 4 步的决策包在“待签版本”里把它们的链接和版本一并列出。

**完成这一步。** 需求文档和 Eval Set 都齐了，产品 +2 请书记员确认节点：

```text
登记请求
- 确认节点：#<研究任务 ID>，由 <产品 +2 的会话名> 提出，必填项：需求文档=<链接>，评测集版本=<版本>
```

后续任务沿用前一条的需求文档和 Eval Set 时，填同一组链接和版本。

## 第 4 步：规格、假设和阈值

**规格。** 算法 +2 起草，写在 `spec/spec.md`。它写实验本身：可改范围、目标指标、实验资源、搜索方法、来自需求文档的约束，再加“假设和阈值”一节。初始化生成的草稿里没有这一节的，加在“目标指标”后面。

“假设和阈值”一节写这几项：

| 项 | 写什么 |
| --- | --- |
| 假设 | 这条任务要检验的说法，一句话，能被一次评测判定 |
| 指标和划分 | 用哪个指标，在正式集上算，几个种子怎么合成一个分数；和评测协议一致 |
| 阈值 | 正式分对照的数字；成立、不成立、无法判定各自的条件都写明 |
| 波动估计 | 基线的方差，或每个结果重复跑几次。阈值不带波动估计，结论容易落在噪声里 |
| 依据 | 阈值从哪来：基线任务的结果（写工作项 ID）、公开数字、需求文档的成功判据 |

- 项目的第一条验证任务是“复现并测量基线”，阈值写成和公开数字相差多少以内。后面的任务拿它的结果定阈值。
- 结论只对照这里签过字的阈值：第 8 步由算法序列写结论，成立、不成立、无法判定三选一。对照用的是质量序列出的正式分；实验方自己跑的是开发分，只用来调试，不写进结论。
- 总预算写进“实验资源”，数字填进研究任务的“总预算”字段，这个字段只收数字。

**请质量序列核对阈值。** 算法 +2 发跨序列的需求包给质量 +2，请它对照评测协议核对“假设和阈值”；质量 +2 交付核对结果。两个序列谈不拢的，写决策包交研究员裁决。

**签字。** 算法 +2 写决策包：

- 包头写“所属研究任务：#<研究任务 ID>”。
- “待签版本”写明签的是这条研究任务的第 4 步，列出要一起冻结的东西和各自的版本：目标和成功标准、需求文档、评测集版本、规格、总预算。
- 草稿经入口进决策队列；研究员在聚焦会话里当场签的，渠道写“研究员主动发起”。研究员批准后，书记员确认这条决策的“决定”这一步，“签字结果”填批准；入口把决策的工作项 ID 交给算法 +2。

**完成这一步。** 算法 +2 请书记员确认节点，“假设签字”填那条决策的工作项 ID：

```text
登记请求
- 确认节点：#<研究任务 ID>，由 <算法 +2 的会话名> 提出，必填项：规格=<链接>，规格版本=<版本>，总预算=<数字>，波动估计=<一句话>，假设签字=<决策工作项 ID>
```

确认之前，脚本核对“假设签字”填的那条决策：是决策工作项，已经决定，签字结果是批准，所属研究任务是这一条，并且是在任务走到第 4 步之后决定的。有一项对不上就停下。所以决策包等任务走到第 4 步再送，提前签的那条到时候用不上。

## 签字冻结什么，签字以后怎么改

第 4 步签字以后，前四步的产出就冻结了：

- 目标和成功标准
- 需求文档
- 评测集版本
- 含假设和阈值的规格
- 总预算

要改只有两条路，都要研究员决定：

1. 退回到第 4 步或之前，改完重新签字。提出的 +2 写决策包，写明退到哪一步、为什么；研究员批准后书记员回滚节点，被退回各步的必填字段会清空，这几步重做一遍再确认。
2. 结束这条任务，另开一条，新任务的来源工作项指向它。

书记员确认“得出结论”之前，脚本读操作记录，核对签字以后冻结的字段有没有被改过，网页上手工改的也查得到。被改过就停下并列出改动，书记员报给入口，等研究员决定。

规格签字后冻结；实验方案是规格范围内的具体安排，在第 5–8 步之间可以修订。一处改动算哪边，看它动没动规格里的条款：动了就是改规格，走上面两条路。

## 第 5 步：实验方案

实验方案由算法 +2 写，在规格定下的范围里安排怎么跑：

- 跑哪些变体，各自和什么对照。
- 运行顺序：先跑最便宜的证伪实验。
- 每一段的预算，加起来不超过签过字的总预算。
- 每个结果重复几次、用哪些种子，照规格和评测协议。
- 开发集上怎么看分数，哪个结果在什么时候交质量序列出正式分。正式集每一轮只跑一次。
- 运行怎么记：所有运行都进台账，失败的也算。每个变体的结果和运行 ID 列在交付包的“证据和来源”里，研究任务的“运行 ID”填这一轮的。

草稿写到 `packages/drafts/alg/YYYYMMDD-实验方案-<简称>.md`，请书记员上传到研究任务单下面，再确认节点：

```text
登记请求
- 确认节点：#<研究任务 ID>，由 <算法 +2 的会话名> 提出，必填项：实验方案=<链接>，实验轮次=<第几轮>
```

- 方案定了以后，算法 +2 发跨序列的需求包：给工程 +2 写搜索流程、运行记录格式和重复次数；给基础设施 +2 写要由运行环境强制执行的约束。约束工程的规则由算法 +2 直接交给基础设施 +2，不经工程转交。
- 第 5–8 步之间可以修订实验方案，不用重新签字。修订后把新版本交书记员，并告诉受影响的工程 +2 和基础设施 +2。
- 第 5–8 步通常要走好几轮。再来一轮，是把研究任务退回到第 5 步，退回由研究员决定；重做第 5 步时，“实验轮次”填这是第几轮。

## 任务文件里的几项

hook 和 CLAUDE.md 用的是任务文件里的这两项，要和文档一致：

- `editable_paths`：可改范围的可写路径，只有工程序列能写。
- `protected_paths`：评测协议用到的只读路径，比如评测脚本和评测集。

放在项目目录以外的评测数据不写进任务文件：在评测协议的“存放和版本”里写明在哪个系统、ID 和固定的版本号。hook 管不到这些数据，靠评测协议、CLAUDE.md 里的约定和账号权限。

要改的几项列进请求签字的决策包。研究员同意后，在普通会话里用 `solo-lab:setup` 改任务文件、重跑 `init --apply`，hook 和 CLAUDE.md 才会跟上。agent 不直接改 `spec/task.json`。

## 拿不准时

- 目标或成功标准还没定：先回研究任务单（`solo-lab:charter`），不在规格里替研究员定方向。
- 还没有基线分数，阈值定不出来：这条任务先做成“复现并测量基线”，阈值写成和公开数字相差多少以内。
- 写不出判据，只想先看看方向：开一条试探任务。试探流程不冻结、不签字、不出正式分，产出是值得验证的假设。
- 项目没有启用算法序列：hook 不让任何角色改 `spec/spec.md`，实验规格由研究员本人写，问题单照样可以用。
- 评测数据只放在项目目录以外：正本最好在项目里也存一份，记下版本和校验和；外面的 ID 和版本号写进评测协议的“存放和版本”。
- 存放数据的系统分不出开发集和正式集：分成两份数据，或者用条目标签区分，划分规则写进评测协议的“划分和可见性”。
