# 开一条研究任务

研究任务是台账的主线。一条研究任务回答一个问题，目标、成功标准、预算、需求文档、规格和结论都记在它上面；研究任务单是它的主文档。本技能管到登记为止：问清研究员要回答什么问题，写研究任务单，请书记员登记。登记以后每一步谁负责、必填什么，以飞书空间为准，用 `ledger.py next <工作项 ID>` 现读。

开之前先看空间里已有的研究任务。同一个问题已经有一条没归档的，接着推进那一条，不再开第二条：

```bash
python3 -I .claude/solo-lab/bin/ledger.py query tasks
```

## 初始化时登记的那一条

初始化时书记员已经登记过一条研究任务。它的研究任务单是照项目名和一句话描述生成的，草稿在 `packages/drafts/pmo/研究任务单-首条.md`，工作项停在第一步。这一条不另开，把它的研究任务单补全：

1. **入口访谈研究员。** 这一条的发出方是研究员，没有哪个序列的 +2 是它的作者，所以由入口来问，问法照下面“先问清，再写”。入口照研究员的原话整理，不替他定目标和判据。
2. **修订稿另存成新的草稿文件。** 比如 `packages/drafts/pmo/YYYYMMDD-研究任务单-<简称>.md`。开头几行这样写：
   - “流程”和原来一样。流程在新建工作项时选定，换不了。
   - “发出方”照旧写 `研究员`。
   - “关联工作项”写 `待建`，或者写这条研究任务的工作项 ID。
3. **请书记员修订。** 给书记员发登记请求，写明草稿路径、这条研究任务的工作项 ID 和改了什么。ID 在首条草稿的“关联工作项”一行，`ledger.py query tasks` 也查得到。书记员先预览，再加 `--apply`：

   ```bash
   python3 -I .claude/solo-lab/bin/ledger.py revise <那条研究任务的工作项 ID> <修订稿> --note '<改了什么>'
   ```

4. **把主文档链接给研究员。** 修订是原位的：工作项的 ID、流程、评论都在，文档还是那一篇，链接不变，开头换成修订稿，交接记录多一行；标题变了的，工作项名称和文档标题一起改。入口把主文档的飞书链接给研究员，他在文档上批注；批注怎么读、怎么转，见下面“请研究员看”。研究员没有意见了，入口再告诉第一步的负责方接着推进：验证任务的第一步“确定目标”归产品 +2。

- 这条研究任务还在第一步时才能换。第一步确认以后脚本报“已经过了第一步…”：后面的改动写进各步自己的产出文档，要改目标照“登记以后要改目标、成功标准或范围”办。
- 想改走试探流程：流程换不了。另开一条研究任务，初始化的那一条请研究员在网页上终止。
- 访谈之前就有 +2 要开别的研究任务：照下面的正常做法另开一条，不占这一条。

## 谁来写

- 验证任务由哪个 +2 写，研究员定；没有特别交代时是产品 +2，因为验证流程的第一步“确定目标”由产品序列负责。
- 试探任务由提出这次试探的那个 +2 写。它是这条任务的发出方，流程里由发出方负责的步骤都归它。
- 研究员在入口说要开新任务时，入口先问清交给哪个序列（路由决策表的 R4），再由那个 +2 用本技能访谈研究员；研究员也可以直接点开那个 +2 的会话谈。入口、路由和书记员只管转交和登记，不写研究任务单的内容；初始化时登记的那一条除外，见上一节。

## 先定走哪个流程

| 流程 | 什么时候用 | 怎么走 | 产出 |
| --- | --- | --- | --- |
| 验证 | 有判据、要下结论 | 确定目标 → 准备上下文 → 准备 PRD 和 Eval Set → 确定假设条件 → 设计实验方案 → 搭建实验平台 → 跑 Eval Set → 得出结论 → 下一步讨论 → 归档；第 4 步和第 9 步要研究员签字 | 结论，成立、不成立、无法判定三选一 |
| 试探 | 还没有假设，只为找方向，比如读代码、小规模试跑、看错误样例 | 定方向 → 试探 → 提出假设 → 归档；不冻结、不签字、不出正式分 | 值得验证的假设 |

- 研究员说不清走哪个时，问两句：做完以后要不要给出成立或不成立的结论，判据现在写不写得出来。两样都有走验证，缺一样走试探。
- 一条验证任务只回答一个能被一次冻结的评测回答的问题。多个问题开多条，后一条用“来源工作项”指向前一条。
- 一个项目的第一条验证任务定为“复现并测量基线”：成功标准写成和公开数字相差多少以内，后面的任务拿它的结果定阈值。
- 试探得出的假设要下结论，另开一条验证任务，来源工作项指向这条试探。
- 论文和汇报材料的写作不开研究任务，走需求包，对外材料归外联序列。

两个流程每一步的负责角色和必填项，对照表在项目的 `org/phases.md`。

## 先问清，再写

一次问一个问题。研究员答不上来的写“待定”，不替他编；代码库、数据和已有运行记录里查得到的先查，不拿去问。

1. 目标：要回答什么问题，为什么现在做，结果给谁用。
2. 成功标准：做成了算什么，写成数字或可检查的条件。要在出结果之前写下，事后定的标准容易向结果靠拢。还没有基线分数时，写成和公开数字相差多少以内。试探任务不问这一条，改问想弄清什么，写进目标。
3. 范围：包含什么，明确不做什么，到什么程度就不再追加投入。
4. 资源上限初值：总预算的数字和单位、期限、超了谁叫停。验证任务的总预算到第 4 步签字时才定下并冻结，这里先记初值；试探任务的总预算在第一步就要填，是这次试探的上限。执行环境和计算资源（在本机、Docker 还是集群上跑，用多少卡）会定下付费运行的条件，研究员已经用决策定了的，记下决策 ID；没定的写“待研究员确认”，不替他限定。
5. 已知的上下文：研究员已经知道的代码、数据、评测脚本和公开数字在哪里，以前试过什么。
6. 风险和未决事项：可能让这条任务做不成的事，还没定的事由谁在什么时候定。
7. 是不是接着前一条任务开的：是的话记下前一条的工作项 ID。

## 写研究任务单

照 `assets/charter.md` 的模板写。标题和开头几行是登记脚本的约定，照模板的写法：

```markdown
# 研究任务单：<任务名>

- 流程：验证
- 发出方：<序列> +2（<会话名>）
- 关联工作项：待建
```

- “流程”写 `验证` 或 `试探`，只写一个。
- “发出方”写成 `产品 +2（Product-p2-01）` 这样；研究员自己开的写 `研究员`，这条任务的序列记成项目管理。
- “关联工作项”在登记前写 `待建`，登记后脚本换成工作项 ID。
- 接着前一条任务开的，加一行 `- 来源工作项：#<前一条的工作项 ID>`。
- 正文要有“目标”一节：登记时它成为状态包的简介，路由靠它判断没带工作项 ID 的信息归不归这条任务。
- “资源上限”一节的“执行环境”和“计算资源”两行写“待研究员确认”，或者写定下它的决策 ID，比如 `- 执行环境：本机 Docker（决策 #2140）`。这两样会定下付费运行的条件（不可逆事项的判据 4），即使是试探任务也要进决策队列：还没定的，由要用它的 +2 写决策包交研究员定。写了具体内容却没有决策 ID，登记时脚本会打印提示：执行环境要进决策队列。

草稿存到 `packages/drafts/<序列>/YYYYMMDD-研究任务单-<简称>.md`。写完先请书记员登记，再把主文档的飞书链接给研究员看：研究员在飞书文档上批注，不看本地文件。研究任务的第一步本来就是写研究任务单，工作项停在这一步等研究员确认；他不同意开这条任务，由他在网页上把工作项终止。

## 请书记员登记

给书记员 `PMO-p0-01` 发【登记请求】：

```text
登记请求
- 草稿：packages/drafts/<序列>/<文件>.md
- 动作：新建工作项并上传
```

书记员运行 `ledger.py register <草稿路径>`：按“流程”一行建“研究任务”工作项，把研究任务单上传到知识库的“研究任务”节点下当主文档，补上状态包和交接记录，再把工作项 ID 写回草稿的“关联工作项”。登记不成时脚本会说缺什么：开头缺行、流程名对不上、“关联工作项”写的不是 `待建`。照提示改草稿，再请书记员重跑。占位没换掉、序列名写错这类问题脚本不一定拦得住，发登记请求之前照模板里的核对清单过一遍。

## 登记以后

```bash
python3 -I .claude/solo-lab/bin/ledger.py next <工作项 ID>
```

这条命令列出现在走到哪一步、由谁负责、还缺哪些必填项。负责这一步的 +2 把产出备齐，再给书记员发登记请求确认节点：

```text
登记请求
- 确认节点：#<研究任务 ID>，由 <你的会话名> 提出，必填项：<字段名>=<值>
```

- 验证任务的第一步“确定目标”由产品 +2 推进，必填的成功标准取自研究任务单的“成功标准”一节。内容长的，登记请求里给文件路径，书记员用 `--set 成功标准=@<文件>` 读。之后的需求文档、Eval Set、规格和实验方案，用 `solo-lab:spec`。
- 试探任务的第一步由发出方的 +2 推进，要填的试探问题和总预算取自研究任务单。试探的事在序列内用需求包委托；要下结论时另开验证任务。
- 配合方的活由负责这一步的 +2 发跨序列的需求包去请，写法见 `solo-lab:packages`。

## 请研究员看

登记好以后，把主文档的飞书链接交给研究员：他在你的会话里的，直接给；不在的，发【通知】请入口转交。研究员在文档上批注。他说批完了，把批注读出来（含已解决的，每条带着它挂的原文）：

```bash
lark-cli drive +list-comments --url <主文档链接> --solved-status all --as user
```

照批注改出修订稿，另存一份草稿，请书记员修订：`ledger.py revise <工作项 ID> <修订稿> --note '<改了什么>'`。修订是原位的，文档链接不变。批注只是讨论的一种方式，不用逐条登记处理结果；改完告诉研究员改了什么就行。

研究任务过了第一步也能这样修订。这时后面各步已经定下的文档不会跟着变，改之前先看要不要一起改。

## 登记以后要改目标、成功标准或范围

- 改这三样会改变其他会话的做法，要研究员决定：提出的 +2 写决策包；研究员当场定下的，渠道写“研究员主动发起”。批准后请书记员用 `ledger.py update` 把“成功标准”这类字段改过来；研究任务单的正文要跟着改的，写修订稿请书记员 `ledger.py revise`。
- 验证任务第 4 步签字以后，目标和成功标准已经冻结。要改只有两条路，都要研究员决定：退回到第 4 步或之前，改完重新签字；或者结束这条任务，另开一条。细则见 `solo-lab:spec`。
- 试探任务不冻结，改动照第一条办。
