# 台账

飞书项目记一件事走到了哪一步，飞书文档记这件事的内容。读写都走项目里的 `.claude/solo-lab/bin/ledger.py`，在项目目录里运行。

五类工作项（研究任务、同序列需求、跨序列需求、决策、反馈）都是节点流程，每个流程以书记员确认的“归档”节点收尾。有哪些流程、节点怎么排、每一步谁负责、必填什么，以飞书空间为准，脚本运行时现读，规则文件里不写。所以推进一步之前先问空间，不照记忆里的流程做。

- 每条命令的参数、输出和报错：`references/commands.md`。
- 五类工作项和主文档、槽位、知识库节点树，去哪里看本项目的流程和字段：`references/structure.md`。

## 读：谁都能用

```bash
python3 -I .claude/solo-lab/bin/ledger.py get <工作项 ID>            # 类型、流程、状态、名称和有值的字段
python3 -I .claude/solo-lab/bin/ledger.py next <工作项 ID>           # 走到哪一步、这一步谁负责、还缺什么
python3 -I .claude/solo-lab/bin/ledger.py query queue               # 决策队列：待决定的决策（已到期、继续等研究员的标“待决定（已到期，继续等研究员）”，排在最前），和研究员定了、执行方是研究员、还没归档的（标“待执行”），每行带版本、紧急程度、回复期限、执行方、研究员要做的事和主文档链接
python3 -I .claude/solo-lab/bin/ledger.py query blocked             # 阻塞原因非空的研究任务和需求，每行带阻塞原因和主文档链接
python3 -I .claude/solo-lab/bin/ledger.py query verifying           # 待验收的同序列需求
python3 -I .claude/solo-lab/bin/ledger.py query open --sequence alg # 进行中的同序列需求，只看算法序列
python3 -I .claude/solo-lab/bin/ledger.py query cross               # 进行中的跨序列需求
python3 -I .claude/solo-lab/bin/ledger.py query tasks               # 没归档的研究任务
python3 -I .claude/solo-lab/bin/ledger.py query recent              # 近 7 天更新过的同序列需求
python3 -I .claude/solo-lab/bin/ledger.py query source:<工作项 ID>   # 由某个工作项引出的工作项
python3 -I .claude/solo-lab/bin/ledger.py trace <工作项 ID>          # 沿来源工作项往回查
python3 -I .claude/solo-lab/bin/ledger.py status <工作项 ID>         # 主文档的状态包
python3 -I .claude/solo-lab/bin/ledger.py mql queue                 # 只打印 MQL，不查
```

- 命令里的工作项 ID 写数字，不带 `#`：shell 把 `#` 开头的词当注释。
- 这些查询都不含“已终止”的工作项。每页 50 项，多的自动翻页；输出读不懂时停下报错，不当成空结果。
- `--sequence` 写序列的标识或中文名：product、alg、rnd、infra、quality、pmo、liaison，或者“算法”这样的中文名。
- 文档用 `lark-cli docs +fetch --doc <链接> --as user` 读。先读大纲（`--scope outline --detail with-ids`）拿到块 ID，再只读需要的那一节（`--scope section --start-block-id <ID>`），省上下文。

## 推进之前先问空间

```bash
python3 -I .claude/solo-lab/bin/ledger.py next 2101
```

```text
#2101  研究任务·验证  确定假设条件  复现并测量基线
  这一步：确定假设条件（set_hypothesis），负责方：算法 +2
    待填 假设签字（hypothesis_signoff）
    待填 规格
    待填 总预算
    待填 波动估计
    待填 规格版本
    “假设签字”填一条研究员批准的决策工作项的 ID，确认前由脚本核对
  下一步：设计实验方案
  书记员推进：ledger.py confirm 2101 --by <会话名>
```

这是一条验证任务走到第 4 步时的输出，节点和字段以你的空间为准。

- 第一行是工作项 ID、类型和流程、状态、名称。
- “这一步”是进行中的节点和它的负责方。下面每行一个完成时必填的字段，标着“已填”或“待填”；约定里的字段后面带着括号里的槽位标识。
- “书记员推进”是接下来该跑的写命令；走到最后一步时写的是 `archive`。
- 工作项记着阻塞原因时，多一行“阻塞中（<日期> 起）：<原因>”。

负责方决定谁可以请书记员推进这一步。`--by` 写提出请求的会话名，脚本拿它和负责方比对。同序列需求的“开工”是个例外：它由委托方在登记请求里写“开工：是”代承接方提出，`--by` 写承接方的会话名：

| `next` 里写的负责方 | 谁来提 |
| --- | --- |
| `<序列名> +2`，比如“算法 +2” | 这个序列的 +2 会话，比如 `Alg-p2-01` |
| `发出方（<会话名>）`、`承接方（<会话名>）` | 括号里的那个会话，或者它所在序列的 +2 |
| `承接方（<序列名> +2）` | 这个序列的 +2 会话 |
| `研究员`、`发出方（研究员）` | 只有研究员，写 `--by 研究员` |
| `…（工作项上还没记是谁）` | 脚本不拦，写上提出请求的会话名 |
| `书记员` | 书记员自己做，不用 `--by` |

研究员交代的事，哪一步都可以写 `--by 研究员`。

不是书记员的会话只读。这一步归你负责时，把产出备齐，再给书记员 `PMO-p0-01` 发【登记请求】：

```text
登记请求
- 确认节点：#<工作项 ID>，由 <你的会话名> 提出，必填项：<字段名>=<值>
```

## 写：只有书记员

写命令加了 `--apply` 才写，只有书记员能运行，别的会话运行会被 hook 拦下。不加 `--apply` 是预览，什么都不写，哪个会话都能跑：想看一份修订稿会换掉主文档的哪一段，自己预览就行，不用请书记员代跑。每条写命令先不加 `--apply` 跑一遍，核对打印出来的 meegle 和 lark-cli 命令，再加 `--apply` 执行。

| 要做的事 | 命令 | 会做什么 |
| --- | --- | --- |
| 登记需求包、决策包、研究任务单、反馈 | `register <草稿> [--task <ID>] [--source <ID>] [--set <字段>=<值>] [--resume] [--doc <链接>\|new]` | 先检查草稿、流程、父节点和新建时的必填字段，有一样不行就不建。建工作项，各角色都填研究员本人；决策包包头的“执行方”和“研究员要做的事”写进同名字段，空间里没有这两个字段就不写；把草稿上传成主文档，补“状态包”和“交接记录”；主文档链接写回工作项，加一条登记评论，工作项 ID 写回草稿。带 `--existing <研究任务 ID>` 时不新建工作项：把研究任务单的修订稿换成这条研究任务的主文档，原来那份留在原处；它还在第一步时才能换 |
| 修订已经登记的需求包、决策包、研究任务单 | `revise <ID> <新草稿> --note '<改了什么>'` | 见“修订” |
| 登记交付包 | `reply <草稿> [--doc <链接>\|new]` | 上传到它答复的那条需求的主文档下，链接写进“交付包”字段；不新建工作项。验收不通过、改好后重新交的，包头“版本”加 1 再 `reply`：新建一份文档，字段换成新链接，上一版留在原处 |
| 确认当前这一步 | `confirm <ID> --by <会话名> [--set <字段>=<值>] [--option <选项>] [--executor <会话名>]`；可逆的决策到期没定用 `confirm <ID> --by 到期默认` | 见“确认节点” |
| 退回到已完成的一步 | `rollback <ID> --to <节点> --reason '<原因>' --by <会话名>`；研究任务用 `--decision <决策 ID>` | 见“回滚” |
| 归档 | `archive <ID>` | 见“归档” |
| 改字段、写阻塞 | `update <ID> --set <字段>=<值>` | 值留空是清空这个字段 |
| 评论 | `comment <ID> --text '<内容>'` | 开头没有会话标签的自动补 |
| 修正主文档里的“关联工作项”一行 | `relink <ID>` | 原位替换那一行，文档身份和链接不变 |
| 替换状态包 | `status-block <ID> --file <文件>` | 整段替换主文档里“状态包”到“交接记录”之间的内容 |
| 追加交接记录 | `append <ID> --file <文件>` | 第一行要带会话标签；追加到文末 |
| 建知识库节点 | `ensure-node <键>`、`ensure-node all` | 知识空间里已有同名节点就直接用，没有才建，写进 `feishu/ids.json` |

### 确认节点

```bash
python3 -I .claude/solo-lab/bin/ledger.py confirm 2101 --by Alg-p2-01 --set 实验轮次=1 --set 实验方案=<文档链接>
```

- `--by` 写提出请求的会话名，它要是这一步的负责方；研究员交代的写 `--by 研究员`；“开工”写承接方的会话名。
- 必填字段用 `--set` 传。之前已经用 `update` 或 `reply` 填好的不用再传；还缺什么，脚本问过空间以后列出来。
- 脚本先做完全部核对，再写字段、确认节点，然后回读：节点要是已完成，并打印现在走到哪一步、什么状态。
- 最后一步不用 `confirm`，用 `archive`。
- 决策确认了“决定”这一步，输出的最后一行是“执行方：<研究员或会话名>。”，取自登记回执，也就是决策包包头的“执行方”；这次确认加了 `--executor` 的，是改成的那个会话。书记员接着通知执行方：执行方是会话的，把决定内容发给它，请它照决定执行，执行完马上请书记员归档；它就是这次的请求方的，写进回执，不另发。执行方是研究员的，不另发，入口按清单列给研究员。
- 确认决策的“决定”时，可以加 `--option` 写研究员选的选项（选项表第一列的名字；带空格的加引号，比如 `--option '本机 Docker'`），表里一个都没选写 `--option 无`。它只是记录：脚本核对选项名，记进回执的 `option`，再加一条评论，带上这个选项列的不可逆的动作；不加也能确认。hook 不看它，不可逆事项清单里的命令 hook 都不拦。
- 确认决策的“决定”时，可以加 `--executor <会话名>` 改执行方：包头“执行方”写的是研究员、研究员选的选项却不用他动手时用。只收各序列的 +2、入口和路由，过和包头一样的检查；要改成研究员的，脚本拒绝，请发出方写下一版，`revise` 以后再确认。生效以后回执的 `executor` 是这个会话、`researcher_action` 是 null，空间里有“执行方”“研究员要做的事”两个字段的随这一步写成会话名和“无”，再加一条评论；之后照执行方是会话的规矩走，`query queue` 不再把它列成等研究员执行。这条决策回滚到“待决定”时，执行方改回包头写的。
- `confirm <ID> --by 到期默认`：可逆的决策登记满到期时长还没定，按包头的到期默认动作记成决定。脚本核对它还在待决定、在本地决策状态里、执行方是会话又不用研究员亲手做事、可逆、没有回滚过（研究员定过一次、又回滚到待决定的决策不再走到期默认，一直等研究员）、登记满到期时长、到期默认动作指向选项表里的一个选项，有一样不满足就停下，什么都不写。都满足时，决定内容写“到期默认：<选项>：<做法>（登记后 <时长>内研究员没有决定）”，决定人填研究员（这个字段只能填人），再加一条同样内容的评论。到期时长写在 `org/decisions.md` 插件那一节，研究员可以改，脚本每次现读，改了马上生效；读不到按 24 小时。不要带 `--set`、`--option`、`--executor`、`--decision`。

### 修订

```bash
python3 -I .claude/solo-lab/bin/ledger.py revise 2140 packages/drafts/infra/20261122-决策包-隔离方式-v2.md --note '去掉同账号沙箱：沙箱规则调不完'
```

- 发出方写了已经登记的需求包或决策包的下一版：新草稿是主文档开头到“状态包”之前那部分改好的样子，包头“版本”比上一版大 1，“关联工作项”写这条工作项的 ID 或“待建”。研究任务单也用它：不写“版本”，脚本自己数；过了第一步也能修订，输出里提醒一句后面各步定下的文档不跟着变（`register --existing` 停用了）。交付包不用它（改好后包头“版本”加 1，用 `reply` 重新交）。修订稿没有“# <包名>：<事项>”标题行的，事项照旧。
- 脚本先核对：包类型、关系都和工作项登记的一致，草稿过包检查，版本号是上一版加 1，决策还在“待决定”，别的包的工作项还没关闭。有一样不过就停下，什么都不写。
- 然后把主文档从开头到“状态包”标题之前整段换成新草稿，“状态包”和“交接记录”保留，交接记录追加一行“[PMO+0] 第 N 版（日期）：<改了什么>”。文档链接不变，旧版本留在飞书文档的历史版本里。
- 工作项的紧急程度（需求包是写了日期的回复期限对应的截止时间）、决策的执行方和研究员要做的事（空间里有这两个字段时）、回执和本地决策状态跟着新版本更新；到期时长照旧从第一次登记算。修订稿里的“关联工作项”写回成工作项 ID，它不会被当成新包再登记。中途失败的，报错写明已经写了什么：修好后重跑同一条命令接着做，交接记录不会多出一行。
- 修订不推给研究员：他下次来谈时，`query queue` 的那一行显示新的版本号。

### 本地决策状态

`.claude/state/gates.json` 只记决策队列来、还在待决定的决策：事项、紧急程度、登记时间、可逆性、到期默认动作、版本、选项表、冻结的动作，回滚过的另记回滚的时间。登记、修订时写进去，确认“决定”、归档、终止时移出；回滚到“待决定”的重新写进去，并记下它回滚过：定过一次的决策不再走到期默认，一直等研究员。只有书记员跑的 `ledger.py` 加 `--apply` 时写它。inbox hook 照它每轮给池会话一行冻结提示、给入口到期提示；guard hook 不读它，冻结的动作和不可逆事项清单里的命令 hook 都不拦，靠各会话照规则办。到期时间不存在文件里：每次用登记时间加 `org/decisions.md` 现写的到期时长算。1.0.4、1.0.5 写的文件里的放行记录读的时候忽略，下次写的时候丢掉。研究员主动发起的决策不进待定决策，补位请求也不进。

### 回滚

```bash
python3 -I .claude/solo-lab/bin/ledger.py rollback 2103 --to 执行 --reason '第 2 条验收标准没有证据' --by Product-p2-01
python3 -I .claude/solo-lab/bin/ledger.py rollback 2101 --to 设计实验方案 --reason '第 1 轮方案漏了对照组' --decision 2110
```

- `--to` 写一个已完成的节点，名字或节点 ID 都行。`--reason` 必填，原因进操作记录。
- 需求、决策、反馈的回滚由工作项当前这一步的负责方提出，`--by` 照确认时的规则核对。验收不通过，是发出方请书记员回滚到“执行”；跨序列需求不接，是承接方回滚到“提出”。工作项只剩归档没做时，由要退回的那一步的负责方提出。
- 研究任务的回滚由研究员决定。退到哪一步、为什么，先写成决策包；研究员批准后带 `--decision <决策工作项 ID>`，脚本照签字的规则核对这条决策。
- 已经归档的要重新打开：需求、决策、反馈只接研究员交代的，写 `--by 研究员`；研究任务照样带 `--decision`。
- 需求、决策、反馈的回滚不走决策，带了 `--decision` 脚本会停下。
- 回滚以后，从退回的那一步到原来所在的那一步，各步的必填字段都清空，新建时就必填的字段留着。旧值打印在输出里，也留在操作记录里。这几步要重做才能再确认。
- 决策回滚到“待决定”：决策队列来的重新进本地决策状态，冻结的动作重新生效；它定过一次，不再走到期默认，一直等研究员；登记满到期时长以后，`query queue` 把它标成“待决定（已到期，继续等研究员）”，排在最前。确认时用 `--executor` 改过的执行方，改回包头写的。

### 归档

```bash
python3 -I .claude/solo-lab/bin/ledger.py archive 2103
```

- 工作项要已经走到最后一步：`next` 的“书记员推进”一行写着 `archive`。
- 脚本先把主文档整棵子树移到“归档文档/<序列>”下，移动的是原节点，文档链接不变；再确认最后一步，回读状态是“归档”。
- 没有这个序列的归档节点会停下，先跑 `ensure-node archive/<序列标识>`。
- 文档移好了、节点没确认成的，修好后跑 `archive <ID> --moved`，只确认最后一步。
- 决策归档表示执行完了。执行方是会话的，它照决定执行完马上来请归档。执行方是研究员的（回执里 `executor` 是“研究员”；没有这一项的旧回执，`researcher_action` 有值的算研究员），归档的登记请求要写“由 研究员 提出”，带他说做完了的原话；归档前先 `comment` 记下他做了什么。
- 决策归档或者在网页上被终止，脚本把它移出本地决策状态里的待定决策，冻结解除。

## 确认之前脚本自己核对什么

必填项齐不齐由空间说了算。另有三件事由脚本自己核对，都在写入之前做，有一件不过就停下，什么都不写。

**谁来提。** `--by` 写的会话要是这一步的负责方，规则见“推进之前先问空间”的表。提的人不对，把请求退回去，让负责的会话来提。

**签字字段引用的决策合不合格。** 这一步的完成表单要求填签字字段时，字段里填一条决策工作项的 ID。约定里的签字字段是“假设签字”和“下一步签字”，参考模板把它们放在验证流程的第 4 步和第 9 步。脚本读这条决策，五项都满足才放行：

- 类型是决策。
- 状态是“待执行”（用 2.1.0 及以前的模板建的空间里叫“已决定”）或“归档”。
- “签字结果”是“批准”。
- “所属研究任务”是正在确认的这条工作项。
- 它是在任务走到现在这一步之后决定的：比的是决策“决定”一步的完成时间和任务这一步的开始时间。

第五项让一条决定只用一次。第 4 步的签字签不了第 9 步；回滚以后，原来的签字和批准回滚的那条决定都作废，要研究员就现在这一步重新决定。

脚本只看这五项。这条决策签的是不是这一步的内容，看决策包的“待签版本”一节，对不上就退回请求方。回滚和认可冻结改动时带的 `--decision`，也照这五项核对。

**冻结的字段签字后有没有被改。** 完成表单要求“假设签字”的那一步一完成，它和它之前各步的必填字段就冻结了。确认要求填“结论”的那一步之前，脚本读操作记录，网页上的手工改动也查得到。冻结的字段在签字之后改过，脚本列出每一处改动并停下。把列出的改动报给入口，等研究员决定，只有两条路：

- 回滚到签字那一步或之前，改完重新签字。
- 研究员认可这些改动：写成决策包，批准后重跑 `confirm`，加 `--decision <决策工作项 ID>`。

## 字段怎么写

`--set <字段>=<值>` 可以重复。字段有三种写法，认的是同一个字段：

- 空间里的字段名：`--set 成功标准='留出集准确率不低于 0.85'`。
- 槽位标识，约定里的字段才有：`--set main_doc=<链接>`、`--set blocked_reason=<原因>`。
- field_key：同名字段不止一个时用它。

这个类型有哪些字段，看 `feishu/space.md`；哪些字段有槽位标识，看 `ledger.py get` 的输出，字段名后面括号里的就是。

值按人读的样子写，脚本换成飞书要的格式：日期写 `YYYY-MM-DD`，单选写选项名，开关写“是”或“否”，人员字段只能写“研究员”。值留空是清空这个字段，`@文件` 是读文件内容。完整的写法见 `references/commands.md` 的“值怎么写”。

## 阻塞写在字段里

走到哪一步和卡没卡住是两回事，所以阻塞记在工作项的两个字段里：阻塞原因、阻塞开始日期。没有“阻塞”这个状态。

```bash
python3 -I .claude/solo-lab/bin/ledger.py update 2103 --set blocked_reason='等基础设施批 GPU 配额'  # 同时写阻塞开始日期
python3 -I .claude/solo-lab/bin/ledger.py update 2103 --set blocked_reason=                       # 解除：两个字段一起清空
```

研究任务、同序列需求、跨序列需求有这两个字段。`query blocked` 列出阻塞原因非空的，`next` 的最后一行也会显示。阻塞原因用 `update` 写，不随 `confirm` 写。

## 出错时

报错以“出错：”开头，后面多半写着接下来该跑什么，先照它做。逐条的原因和处理办法在 `references/commands.md` 的“出错时”。

- 预览里的结果行以“预览：会…”开头，最后一行是“这是预览，没有写飞书”。以“登记：”“确认：”“回滚：”“归档：”开头的行才是写成了。
- 写命令超时、或者返回里没有 ID 和链接时，这一步可能已经写进飞书。先在网页上核对，再决定要不要重跑。登记用 `--resume` 和 `--doc` 接着做，归档用 `--moved`，不从头再来。
- “还没绑定飞书空间”“字段还没绑定”这一类是绑定的问题。退回请求方，请研究员照技能 `solo-lab:setup` 绑定，对不上的地方用技能 `solo-lab:space-bind` 处理。书记员不代跑，也不拿别的字段顶替。
- “台账正在被别的写入占用”：等那条命令写完再试，不删锁文件。
- 写入连续失败两次就停，不换着法子重试。把命令、报错原文和返回的 logid 写进异常清单。

## 拿不准时

- 草稿通不过检查、包头读不出必填项：退回请求方，附上检查输出，不替作者改内容。
- 提请求的会话不是这一步的负责方：退回请求方，让负责的会话来提。
- 签字的决策不合格、冻结的字段被改过：把脚本列出的问题报给入口，等研究员决定。
- 来源工作项不存在、已关闭：不登记，退回请求方确认。
- 台账和文档对不上：两边都不改，写进异常清单。
- 终止工作项命令行做不了，要研究员在网页上做。终止以后，会话池认领表里它的条目由入口用 `route.py pool --prune` 对照台账清掉。
