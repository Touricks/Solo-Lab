# 台账结构

> 有哪些流程、节点怎么排、每一步谁负责和必填什么、有哪些字段，都在飞书空间里，脚本运行时读，这里不抄。这里只写不随空间变的部分：五类工作项和各自的主文档、槽位、知识库节点树。“工作项类型”的表和“文档放在哪里”的清单由 `orgspec.py show work-items`、`orgspec.py show docs-tree` 生成，测试会检查它们和规则文件一致。槽位表对着约定文件 `orgspec/contract.json`（`contract_version` 1）和术语表 `orgspec/terms.zh.json` 列出，约定改了以约定文件为准。

## 工作项类型

| 工作项类型 | 主文档 | 挂在下面的答复 | 由谁创建 |
| --- | --- | --- | --- |
| 研究任务 | 研究任务单 | 无 | 书记员 |
| 同序列需求 | 需求包 | 交付包 | 书记员 |
| 跨序列需求 | 需求包 | 交付包 | 书记员 |
| 决策 | 决策包 | 无 | 书记员 |
| 反馈 | 导师或研究员原话所在的文档 | 无 | 书记员 |

- 一份包对应一条工作项。登记需求包、决策包、研究任务单或反馈，就是新建一条对应类型的工作项，这份文档是它的主文档。交付包是答复，不新建工作项，链接填进它答复的那条需求的“交付包”字段。
- 研究任务是主线，一个空间可以有多条。同一个类型可以有不止一个流程，新建时选定；参考模板里研究任务有验证和试探两个流程，其余四类各一个。
- 需求、决策和反馈用“所属研究任务”指向一条研究任务。后续的工作项用“来源工作项”指向引出它的那一条。
- 五类都是节点流程，每个流程以书记员确认的“归档”节点收尾，“归档”是唯一的正常终态。飞书自带的“已终止”不算一步，命令行做不了，要研究员在网页上做。
- 没有“阻塞”这个状态。卡住了，记在工作项的阻塞原因和阻塞开始日期两个字段里。

## 去哪里看这个项目的流程和字段

| 想知道 | 看哪里 |
| --- | --- |
| 一条工作项现在在哪一步、谁负责、还缺什么 | `python3 -I .claude/solo-lab/bin/ledger.py next <工作项 ID>`。现读，以它为准 |
| 每个流程有哪些节点，各自的负责角色和必填项 | `feishu/space.md` 的“流程”一节；或者 `python3 -I .claude/solo-lab/bin/space.py show --target . flows` |
| 一个类型有哪些字段和选项、角色、状态，新建时必填什么 | `feishu/space.md` 里这个类型的一节；或者 `python3 -I .claude/solo-lab/bin/space.py show --target . fields` |
| 研究任务各流程的对照和推进规则 | `org/phases.md` |
| 约定的槽位各绑到了空间里的哪个对象，还缺什么 | `feishu/binding.md`；或者 `python3 -I .claude/solo-lab/bin/space.py show --target . binding` |
| 快照是什么时候读的 | `feishu/space.md` 开头的读取时间 |

- `feishu/space.md` 和 `space.py show` 读的都是快照 `feishu/space.json`。空间配置改过以后要重读，用技能 `solo-lab:space-read`。
- 流程图只能从一条工作项读出来。某个流程还没有工作项时，快照里没有它的节点，登记第一条以后重读。`ledger.py next` 不受这个限制，它读的是这条工作项自己的节点。

## 槽位

脚本要按含义处理的东西叫槽位：主线是哪个类型，主文档的链接存在哪个字段，这一步的负责方是谁，哪个状态算归档。槽位列在约定文件 `orgspec/contract.json` 里，项目里的副本在 `.claude/solo-lab/orgspec/contract.json`，只有英文标识。每个槽位对应这个空间里的哪个类型、字段、角色和状态，记在项目的 `feishu/ids.json`，这叫绑定。

槽位以外的字段，脚本按空间里的名字读写；流程和节点每次现读。所以模板加字段、改流程、改必填项，只要槽位都在，插件不用改。槽位增减时 `contract_version` 加一。

命令里写槽位标识和写空间里的字段名是一回事：`--set main_doc=…` 和 `--set 主文档=…` 写的是同一个字段。

### 类型槽位

| 槽位 | 名字 | 字段槽位 | 角色槽位 | 状态槽位 |
| --- | --- | --- | --- | --- |
| `research_task` | 研究任务，主线 | 10 | 7 | 1 |
| `same_seq` | 同序列需求 | 11 | 3 | 5 |
| `cross_request` | 跨序列需求 | 11 | 3 | 6 |
| `decision` | 决策 | 7 | 2 | 3 |
| `feedback` | 反馈 | 4 | 2 | 1 |

### 字段槽位

| 槽位 | 名字 | 类型 | 脚本要用的选项 | 用在哪些类型 | 脚本拿它做什么 |
| --- | --- | --- | --- | --- | --- |
| `sequence` | 序列 | 单选 | 产品、算法、工程、基础设施、质量、项目管理、外联 | 五类都有 | 按序列筛查询；归档时决定移到哪个序列的归档节点 |
| `sender` | 发出方 | 单行文本 |  | 五类都有 | 记发出方的会话名，“发出方”角色认它 |
| `main_doc` | 主文档 | 链接 |  | 五类都有 | 主文档的链接，读状态包、追加交接记录、归档都靠它找文档 |
| `source_item` | 来源工作项 | 单行文本 |  | 研究任务、同序列需求、跨序列需求、决策 | `trace` 和 `query source:<ID>` 沿着它查；执行关系的需求包挂在它的主文档下 |
| `task_ref` | 所属研究任务 | 单行文本 |  | 同序列需求、跨序列需求、决策、反馈 | 核对签字的决策是不是这条研究任务的 |
| `due` | 截止时间 | 日期 |  | 研究任务、同序列需求、跨序列需求 | 登记时把需求包的回复期限写在这里 |
| `blocked_reason` | 阻塞原因 | 单行文本 |  | 研究任务、同序列需求、跨序列需求 | 非空就算阻塞，`query blocked` 按它查 |
| `blocked_since` | 阻塞开始日期 | 日期 |  | 研究任务、同序列需求、跨序列需求 | 跟着阻塞原因一起写、一起清 |
| `owner_session` | 负责会话 | 单行文本 |  | 同序列需求 | 同序列需求的“承接方”角色认它 |
| `relation` | 关系 | 单选 | 下发、执行 | 同序列需求 | 登记时照包头的关系填 |
| `delivery_link` | 交付包 | 链接 |  | 同序列需求、跨序列需求 | `reply` 把交付包的链接写在这里 |
| `from_sequence` | 发起序列 | 单选 | 产品、算法、工程、基础设施、质量、项目管理、外联 | 跨序列需求 | 登记时填发出方的序列 |
| `to_sequence` | 承接序列 | 单选 | 产品、算法、工程、基础设施、质量、项目管理、外联 | 跨序列需求 | 跨序列需求的“承接方”角色认它 |
| `urgency` | 紧急程度 | 单选 |  | 决策 | 登记时照决策包包头填 |
| `sign_result` | 签字结果 | 单选 | 批准、退回 | 决策 | 签字的决策要是“批准” |
| `hypothesis_signoff` | 假设签字 | 单行文本，签字字段 |  | 研究任务 | 填签字的决策的 ID；要求它的那一步完成后，这一步和之前各步的必填字段冻结 |
| `next_step_signoff` | 下一步签字 | 单行文本，签字字段 |  | 研究任务 | 填签字的决策的 ID |

### 角色槽位

节点的负责角色要是下面九个之一，每个节点正好一个。脚本按它判断谁可以请书记员确认或回滚这一步。

| 槽位 | 名字 | 对应谁 | 用在哪些类型 |
| --- | --- | --- | --- |
| `product` | 产品 | 产品序列的 +2 | 研究任务 |
| `alg` | 算法 | 算法序列的 +2 | 研究任务 |
| `rnd` | 工程 | 工程序列的 +2 | 研究任务 |
| `infra` | 基础设施 | 基础设施序列的 +2 | 研究任务 |
| `pmo` | 项目管理 | 项目管理序列的 +2，也就是入口 | 研究任务、反馈 |
| `issuer` | 发出方 | 工作项的“发出方”字段记的那个会话 | 研究任务、同序列需求、跨序列需求 |
| `assignee` | 承接方 | 同序列需求看“负责会话”字段，跨序列需求看“承接序列”字段 | 同序列需求、跨序列需求 |
| `researcher` | 研究员 | 研究员本人 | 决策 |
| `scribe` | 书记员 | 书记员 | 五类都有 |

### 状态槽位

查询要知道哪些状态算待决定、待验收、归档，所以这几个状态按名字绑定。别的状态脚本只照空间里的名字显示。

| 类型 | 状态槽位 |
| --- | --- |
| 研究任务 | 归档（`archived`） |
| 同序列需求 | 待开工（`queued`）、执行中（`doing`）、待验收（`verifying`）、已验收（`accepted`）、归档（`archived`） |
| 跨序列需求 | 已退回（`returned`）、待接单（`waiting`）、执行中（`doing`）、待验收（`verifying`）、已验收（`accepted`）、归档（`archived`） |
| 决策 | 待决定（`pending`）、已决定（`decided`）、归档（`archived`） |
| 反馈 | 归档（`archived`） |

### 约定里的流程规则

| 规则 | 内容 |
| --- | --- |
| 归档节点 | 每个流程正好一个末尾节点，负责角色是书记员，完成后状态是“归档” |
| 签字 | 签字字段里填一条决策的 ID。这条决策的状态要是“已决定”或“归档”，“签字结果”是“批准”，“所属研究任务”是正在确认的这条工作项，并且是在任务走到这一步之后决定的：一条决策只过一次关 |
| 冻结 | 要求“假设签字”的那一步完成后，它和它之前各步的必填字段冻结；确认要求“结论”的那一步之前核对 |
| 回滚 | 研究任务的回滚要带一条研究员批准的决策 |
| 已关闭的状态 | “已验收”“归档”，加上飞书自带的“已终止”。路由按它判断一条信息还能不能续到这条工作项上 |

## 文档放在哪里

- 空间：每个项目建一个独立的知识空间。
- 一级节点：研究任务、同序列需求包、跨序列需求包、决策包、反馈包、汇报文档、归档文档。
- 按序列再分一层的节点：同序列需求包、归档文档。
- 研究任务放在研究任务节点；各步的产出文档挂在研究任务单下面。
- 下发关系的需求包放在同序列需求节点下的本序列节点。
- 执行关系的需求包放在来源工作项的主文档。
- 交付包放在它答复的那份主文档。
- 跨序列关系的需求包放在跨序列需求节点。
- 决策包放在决策节点。
- 反馈放在反馈节点。
- 上传和归位统一由书记员做。
- 归档时，把主文档的整棵子树移到归档节点下对应的序列，再确认“归档”节点；移动的是原节点，文档身份和链接都不变。
- 执行关系的需求包按验收标准划分，不按运行次数划分；每次运行靠运行 ID 记录。

### 节点树

右边一列是节点的键，`ledger.py ensure-node <键>` 和 `feishu/ids.json` 里用的就是它。

```text
知识空间
├─ 研究任务            research_task
├─ 同序列需求包        same_seq
│  ├─ 产品             same_seq/product
│  ├─ 算法             same_seq/alg
│  ├─ 工程             same_seq/rnd
│  ├─ 基础设施         same_seq/infra
│  ├─ 质量             same_seq/quality
│  ├─ 项目管理         same_seq/pmo
│  └─ 外联             same_seq/liaison
├─ 跨序列需求包        cross_request
├─ 决策包              decision
├─ 反馈包              feedback
├─ 汇报文档            report
└─ 归档文档            archive
   ├─ 产品             archive/product
   ├─ 算法             archive/alg
   ├─ 工程             archive/rnd
   ├─ 基础设施         archive/infra
   ├─ 质量             archive/quality
   ├─ 项目管理         archive/pmo
   └─ 外联             archive/liaison
```

一共 21 个节点：一级 7 个，“同序列需求包”和“归档文档”下面各 7 个序列节点。没启用的序列不建它的节点。

| 登记或归档的东西 | 放在 | 节点的键 |
| --- | --- | --- |
| 研究任务单 | “研究任务”节点下 | `research_task` |
| 下发关系的需求包 | “同序列需求包”下发出方序列的节点 | `same_seq/<序列标识>` |
| 执行关系的需求包 | 来源工作项的主文档下 | 不占节点 |
| 交付包 | 它答复的那条需求的主文档下 | 不占节点 |
| 跨序列的需求包 | “跨序列需求包”节点下 | `cross_request` |
| 决策包 | “决策包”节点下 | `decision` |
| 反馈 | “反馈包”节点下 | `feedback` |
| 归档的工作项 | “归档文档”下这条工作项所属序列的节点，整棵子树一起移 | `archive/<序列标识>` |

“汇报文档”节点放外联序列准备的材料，`ledger.py` 不往里写。主文档的标题是 `工作项 <工作项 ID>｜<包名>（<作者会话名>）：<任务名>`，挂在下面的交付包是 `交付包（<作者会话名>）：<任务名>`。
