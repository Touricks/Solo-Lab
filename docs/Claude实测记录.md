# Claude 实测记录（0.6.0）

> 这份记录写于插件改名之前。文中的 `agent-org` 是 Solo-Lab 当时的插件名，命令和路径照当时的写法保留。文中的“派活”“交回”也是当时的说法，1.0.0 起叫“委托”“交付”，消息抬头【派活】【交回】就是现在的【委托】【交付】。

版本 0.6.0，测试日期 2026-11-12 至 2026-11-13，测试项目 `agent-org-claude-test`（前四轮和流程测试）和 `agent-org-claude-fresh`（第五轮）。名词和日常用法见[使用说明](使用说明.md)，会话池的机制和假设清单见[机制说明](../plugins/solo-lab/skills/setup/references/mechanisms.md)。

0.6.0 的初始化和六个流程都在真实的 Claude Desktop 和飞书环境里走通了，最后按最终版本从空目录又完整初始化了一遍。

- 初始化做了五轮。第一轮从空目录完整走通，19 个会话是平铺开出的；第二到四轮在已有的空间上重开会话池，第四轮按现在的开法（3 批、2 轮）开齐 19 个，19 次开会话没有一次被拒，四层检查就绪。第五轮换一个空目录，用最终版本和模板 2.1.0 从头走完：19 个会话都认领，本地配置、飞书、首条研究任务三层就绪。
- 第五轮测出两件事：初始化会话开在 bypass 模式时，应用每开一个会话都要研究员点一次确认；脚本打印了“将要新建”的清单，初始化会话没有转给研究员。
- 六个流程在第四轮开出的会话池里各走了一遍，9 条工作项都到了“归档”：用时 48 分钟，会话之间发了 114 条消息，研究员回答 3 次。
- 首次耗时有两份，飞书操作都超过 300 秒的指标：第一轮 326.11 秒，第五轮 334.60 秒。
- 链接字段直接传本地文件在真实空间里走了一遍，三步都通过：两次上传得到两份文档，字段填的是后一份，三份文档都挂在任务主文档下面。这一遍由研究员的会话直接运行台账脚本，没有经过会话池。
- 还差：+2 请书记员直接上传这条路没有在会话池里走过。回退档、`meegle` 的扫码登录、别的企业账号用模板建空间没有测。待修的有 1 条；另有 4 条研究员定了这一版不改代码，约定已写进文档。

## 链接字段直接传本地文件

这是流程测试之后加的功能：`ledger.py confirm` 和 `update` 的 `--set <链接字段>=@<本地文件>`，把本地文件传到这条工作项的主文档下面，再把链接填进字段。第五轮结束以后，在第五轮的项目里走了三步。

这一遍没有经过会话池。会话池当时已经归档，研究员同意后，由研究员的会话直接运行台账脚本，确认节点时请求人写“研究员”。所以走通的是脚本对真实飞书这一层。+2 在登记请求里写 `<字段>=@<本地文件>`、书记员照做，这一层只有离线测试。

| 步 | 做什么 | 结果 |
| --- | --- | --- |
| 1 | 确认“确定目标”，填成功标准 | 通过，7 秒 |
| 2 | `update` 上传需求文档，前后三次：先传一次，不改文件再传一次，文件末尾加一行再传一次 | 第一次 5 秒，新建一份文档并填进字段。不改再传，脚本沿用第一次的文档，不新建。加一行以后再传 6 秒，新建第二份文档，链接和第一次不同，字段换成第二份。读回正文：第一份没有加的那一行，第二份有 |
| 3 | 确认“准备上下文”，同一条命令里上传上下文文档 | 通过，10 秒。任务走到“准备 PRD 和 Eval Set”，这一步的必填清单里“需求文档”显示已填 |

三份文档逐个读了知识库节点，上一级都是这条任务的主文档。每次上传各留一份回执。

开始之前先撞上一件事：这个项目的知识空间在测试前已经不在了，带回读的检查报 21 个节点和首条研究任务的主文档都读不到。

- 第 1 步照常通过，它只写飞书项目这一边。
- 第 2 步上传时飞书报找不到上一级节点（`Parent node not found`，错误码 3380002）。脚本先建文档、后填字段，建文档失败就停下：工作项的字段没有被改，也没有留下上传回执。
- 研究员同意后重建。`feishu/ids.json` 里记着旧的知识空间时，绑定不会重新找，所以先手工删掉 `wiki` 下面的 `space_id` 和 `nodes`，再运行 `setup.py feishu --live --apply`（新建同名知识空间，12 秒）和 `ledger.py ensure-node all --apply`（21 个节点，39 秒）。
- 原来那条研究任务已经过了第 1 步，换主文档的命令只在第 1 步能用，所以另登记一条研究任务（9 秒）。上表的三步是在新登记的这一条上走的。
- 重建以后，带回读的检查里飞书一层恢复就绪。

## 实测到的桌面端规则

开池的做法是照这些规则定的。测到它们时应用的版本没有记录。

| 规则 | 怎么测到的 |
| --- | --- |
| 被别的会话开出来的会话，在首轮里可以再开会话，连续接力两跳也行 | 第一轮后的试验（8 个一次性的小会话）三次都成功；第二轮里 11 个该往下开的真实会话都去开了 |
| 被别的会话的消息叫起来的那一轮，应用拒绝开会话，报错以 “Start sessions only on the user's own words to you here…” 开头 | 同一次试验 |
| 嵌在下面的会话跟着上一级一起移动，单独移动会被拒绝；上一级移到顶层以后，下面的会话还嵌在它下面 | 同一次试验；第三、四轮里 +2 先移到顶层再往下开，开出的会话嵌在它下面 |
| 嵌着的会话在侧栏分区里一层一层缩进显示；移到顶层的会话能归入分区 | 缩进显示见于第二轮，归入分区见于第一轮 |
| 会话自己开出的会话，同时最多 5 个在跑。初始化会话在研究员亲口开始的那一轮里开的 +2 不算；+2 开的 +1、+1 开的 +0 算，+1 自己在跑的时候也占一个。同一个初始化会话开出的全部会话合在一起算，把 +2 移到顶层也不改变这个数 | 第二轮撞上；随后的试验（4 组小会话，每组三层）里前 5 个开出，第 6、7 个被拒 |
| 研究员每发一条消息，会话自己开出的会话最多 10 个；初始化会话亲手开的七个 +2 不算 | 第三轮：前 10 个自动开出的都成功，第 11、12 个被拒 |
| 会话移到顶层以后，会话之间的消息照常送达，收方的 hook 都记进了派发日志（机制说明的 P9） | 第四轮重建知识空间时的 8 条消息，流程测试的 114 条 |
| auto 模式下，由别的会话来信开始的那一轮里，派活、写台账、改文件不被拦（机制说明的 P4） | hook 记下前四轮和流程测试的会话都是 auto 模式，流程测试的 114 条消息和 9 条工作项都是这样走完的 |
| 初始化会话是 bypass 模式时，应用对每一次开会话都弹一张确认卡，只有 Deny 和 Allow once。+2 开 +1、+1 开 +0 也一样，卡片弹在发起的那个会话里，没点之前那个会话停着。auto 模式下不弹 | 第五轮：前两批在 bypass 模式下开，每个会话点一次；第 3 批在 auto 模式下开，7 个会话没有确认卡。前四轮没有会话等过这种确认 |
| 会话管理工具能改同一个池里别的会话的权限模式，从那个会话的下一轮起生效；正停在确认卡上的会话改不了 | 第五轮：研究员说“统一成当前模式”，初始化会话把 6 个空闲的会话从 bypass 改成 auto，2 个停在确认卡上的没改成 |

`detach_session` 的工具说明另外写明两条，没有单独测：嵌着的会话随上面那个会话一起归档；移到顶层的会话结束一轮时，开它的会话不再被叫醒。

应用拒绝开会话时，报错里把“另一个会话交给你的任务”也列为不允许，和实测到的行为不一致，所以“首轮里能开会话”这一条在以后的版本里可能收紧。真收紧了，哪一级没开出来，研究员就点开上一级的会话说一句“照认领输出开出下一级”。

## 测试中发现并已修的问题

开池撞上的两条上限和改法见上面五轮的表，其余的在下表。流程测试里入口记下的问题归并成 12 条：8 条已修，4 条不改代码，其中 3 条把约定写进了文档。

| 发现于 | 问题 | 改法 |
| --- | --- | --- |
| 第一轮 | 初始化会话的标题叫 Researcher，它是做初始化的会话，不是入口 | 标题改成 `Initialization` |
| 第一轮 | 初始化会话没有照技能打印“将要新建的东西”。清单写死在技能里，要会话自己抄一遍 | 改成脚本打印：`setup.py announce` 照任务文件和启用的序列算出两个空间的名字、节点数、会话数和中途要研究员做的事，技能第 1 步运行它，把输出原样转给研究员 |
| 第二轮 | 一个 +1 开 +0 被应用拒绝后，改提了一张启动卡 | 认领输出写明两条上限：被拒时这一个先不开，不改提启动卡，回话里写明还差哪一个 |
| 流程测试前 | 对着角色说明、技能和流程表核对出的缺口：交付包谁请书记员上传、谁确认“执行”；验收后谁确认“验收”、谁提归档；书记员接谁的登记请求；“开工”这一步的 `--by` 写谁；链接字段的产出怎么上传；研究任务确认一步后谁通知下一个序列；入口能不能发第 9 步的决策包；决策包模板的“关联工作项”占位；冻结的字段不能直接改；承接方 +2 怎么接单 | 测试前改完，流程测试照改后的说明走通 |
| 流程测试 | 入口请书记员确认决策的“决定”时，说明里没写请求人要写研究员并附原话；研究员在别的会话里给的签字，转述时要核对原话出处，说明里也没写 | 入口的说明写明登记请求由研究员提出、照抄原话；入口先核对出处，书记员缺了出处就退回 |
| 流程测试 | 研究任务单的发出方只写会话名时，脚本认不出序列，记成了项目管理，文档也归到项目管理下面 | 只写会话名时按会话名的简写认出序列 |
| 流程测试 | +2 把结果交回入口、发起方验收后交回入口时，hook 提醒“负责会话不对”，是误报 | 本序列上一级往上交、交回给入口不再提醒，别处来的交回照旧提醒 |
| 流程测试 | 说明里没写清的四处：跨序列需求里承接方确认节点经入口还是直接找书记员；跨序列需求的“序列”字段记哪个序列；入口怎么知道研究任务走到哪了；入口给 +2 交代事情用【通知】还是【派活】 | 统一成经入口，登记请求由入口发；“序列”记承接序列；入口要看进度就查台账，不加通知；有工作项用【派活】，没有的用【通知】，发之前都先查对方空不空 |
| 流程测试后 | 写产出文档这件事 +2 自己就能做，程序却只让 +1 写的交付包上飞书 | 链接字段可以直接给本地文件：`ledger.py confirm` 和 `update` 的 `--set <字段>=@<本地文件>` 把文件上传到这条工作项的主文档下面并填链接；+2 的说明写明验收通过以后才把交付包的链接填进研究任务 |
| 审阅这份记录时 | 验证流程第 7 步必填“试过的变体数”。每个项目的首条任务是复现并测量基线，没有变体可数；没有脚本或决定用到它，流程测试两轮都填 1 | 研究员定：从模板和插件里拿掉。模板升到 2.1.0，第 7 步的完成表单只剩“运行 ID”。成本看“总预算”和“已用预算”，每个变体的结果和运行 ID 列在交付包里 |
| 第五轮 | 初始化会话开在 bypass 模式，每开一个会话都要研究员点一次确认。默认的池要点 19 次，卡片分散在十几个会话里 | 这张卡是应用有意留的确认，不去绕开。`setup.py announce` 写明两种模式下各要点几次；`setup.py pool` 开池前读本会话的权限模式，是 bypass 就先停下，让研究员选：换一个 auto 模式的会话接着开，或者留在本会话逐个点。文档写明初始化会话用 auto 模式 |
| 第五轮 | 脚本打印了“将要新建”的清单，初始化会话没有转给研究员。它把这条命令和开始计时连在一起运行，说的第一段话直接讲建空间 | `announce` 输出的第一行先告诉会话：把清单原样发给研究员，发完再运行下一条命令。技能第 1 步改成先单独运行它、先发清单，再开始计时。会话照不照做脚本管不了，使用说明写明没收到清单时怎么要 |
| 第五轮回读时 | 各会话第一次认领时在命令前多写了 `cd <项目目录> &&`，被 hook 拒一次，重写后才认领上。第五轮 18 次，前四轮合计 62 次 | hook 认“cd 到本项目目录”这一种前缀，和不带前缀的写法一样处理。别的目录、分号、管道照旧拒 |

流程测试里的 8 条修完后，离线回归 441 个用例全部通过；“新建清单由脚本打印”改完后是 446 个，去掉“试过的变体数”后是 447 个，加上权限模式的检查后是 451 个，改完上面两条后是 453 个，补上“书记员带本地文件的台账命令能过 hook”一条后是 454 个。每次改完测试项目都同步过。
